# ทดลองส่งหนึ่งรายการในคิวปกติ #296

เกณฑ์รับงานคือเลือกเฉพาะงาน PENDING ที่ระบุจากเดือนปัจจุบัน อ่านแถวจริงเทียบ D1 ก่อนขยาย เก็บรายการเดิมใน REVIEW และรักษาข้อมูลธุรกรรม ความเสี่ยงสูงเนื่องจากการเปิด epoch ใน D1 อนุญาตให้คิวปกติเริ่มเขียนรายงานได้

ที่ฐาน 0c08c6c คิวปกติและ cron หยุดเมื่อพบ workbook claim ใน REVIEW ส่วนตัวเลือกอัตโนมัติเดิมเปิดงานถัดไปได้หลังจบ epoch แรก การทดลองจึงต้องปิดการเลือกอัตโนมัติ คง recovery gate และ pacing ตรวจ Worker รุ่นเดียว 100% และรอผู้เขียนเดิมหยุด ก่อนส่งคำสั่งต้องตรวจการพัก incident, หลักฐาน DAILY และ notice ตามกระบวนการกู้

ผู้ดูแลเรียก POST `/admin/stable-sync/normal-expense-pilot` ด้วยคำสั่ง HANDOVER_ONE ผ่าน workflow ซึ่งส่งรหัสงานและหลักฐานรายการเดิม พร้อม header `x-malipang-expected-worker-version` ผ่าน admin authentication ปกติ เปิด `CONTINUOUS_NORMAL_QUEUE_PILOT_ENABLED=true` และกำหนด `CONTINUOUS_NORMAL_EXPENSE_RECOVERY_ENABLED=false` ค่าเริ่มต้นปิด pilot ไม่ส่ง job ID หรือข้อมูลธุรกรรมลง log สาธารณะ งานต้องตรงกับแท็บรายวันที่กำหนด เป็น CONFIRMED รุ่น 1 หลัง cutover ผ่านเงื่อนไขการรับงานเดิม และอยู่ในเดือนปัจจุบันตามกรุงเทพฯ

RESERVED ยืนยันเพียงการจองงานใน D1 จากนั้นคิวปกติจะส่งและอ่านกลับ หากผลเปิด epoch ไม่แน่ชัดให้ตรวจ epoch และ admission ใน D1 การเรียกซ้ำจะเปิดงานที่สองไม่ได้แม้งานแรกเสร็จแล้ว ก่อนขยายต้องตรวจ job, epoch, projection, preimage, marker และค่าจริงในแถวเทียบกับ D1 เมื่อหยุดให้คง recovery gate ปิดฟังก์ชันเปิด pilot และตรวจสถานะงานที่ได้รับสิทธิ์ไปแล้ว การปิดฟังก์ชันนี้ไม่ยกเลิก epoch ที่เปิดอยู่

ถ้า lease ของงานทดสอบหมดอายุ cron จะตั้งเฉพาะงานทดสอบและ epoch เป็น REVIEW ด้วยเหตุ CONTINUOUS_SYNC_LEASE_EXPIRED_UNCERTAIN และพัก claim ที่มี operation ตรงกัน เพื่อให้ตรวจผลที่ Google อาจได้รับไปแล้วก่อนตัดสินใจกู้ต่อ

ขั้น READBACK ตรวจสูตร ยอด วันที่ รายละเอียด หมวดหมู่ และกระเป๋าเงินจริงเทียบกับ D1 และอ่านแถวที่เลือกกับคอลัมน์ marker ซ้ำก่อนสรุป หากข้อมูลต้นทางหรือแถวเปลี่ยนระหว่างตรวจ ให้ถือว่า UNVERIFIED ผลตอบผู้ดูแลแสดงเฉพาะสถานะและ Worker version

## UAT และการทดลองบน Production

1. ในระบบทดสอบที่แยกข้อมูล ให้ใช้รายการตัวอย่างที่มี DAILY intent และสถานะ REVIEW ตรงกับกรณีจริง พร้อมงาน PENDING ที่รออย่างน้อยสองรายการ ใช้รูปแบบแท็บเดิมและบัญชีบริการที่ได้รับสิทธิ์ เขียนผลเทียบก่อนและหลัง ทั้งค่าที่แสดงบนชีตและสถานะใน D1
2. เมื่อเปิด recovery gate ให้ปิดการเลือกงานอัตโนมัติและตัวส่งรายเดือน เปิด operator พิสูจน์ DAILY และโหมดทดลองเพียงงานเดียว รอให้ Worker รุ่นก่อนหยุดทำงานและตรวจการงดผู้เขียนอื่นก่อนส่งมอบสิทธิ์ตรวจไฟล์
3. ใช้ workflow normal queue pilot ซึ่งตรวจ main SHA และรุ่น Worker ที่รับ traffic ทั้งหมด เรียก PROBE เพื่อตรวจรายการเดิม ถ้าตรง ให้ SETTLE เพื่อบันทึกเฉพาะหลักฐาน การส่งงานเดิมที่อยู่ใน REVIEW ซ้ำทำให้หลักฐานคลาดเคลื่อนได้
4. HANDOVER_ONE ต้องพบรายการที่เข้าเกณฑ์เพียงรายการที่เลือกและใช้ผลสำรองกับ restore ที่ผ่านสำหรับ SHA นั้น การสำรองที่ได้รับอนุญาตหนึ่งครั้งใช้หลักฐานเดิมของรอบนั้นได้ทั้งสองขั้น คำตอบ RESERVED หมายถึงคิวรับสิทธิ์เริ่มงานแล้ว
5. ตรวจ INSPECT_HANDOVER และ READBACK ด้วยบัญชีของ Worker พร้อมตรวจ job, epoch, operation, failed jobs และจำนวนรายการรอที่เหลือ แถวที่ผ่าน READBACK ยืนยัน DAILY เท่านั้น งานที่ยังมี RAW หรือ DETAIL ค้างให้รายงานแยก เมื่อผลเขียนไม่แน่ชัดให้คงรายการไว้เพื่อตรวจต่อ
6. หยุดการขยายเมื่อ source หรือแถวที่อ่านกลับเปลี่ยน งานอื่นได้รับสิทธิ์โดยไม่คาดหมาย หรือ worker version เปลี่ยน หลังเกิดความไม่แน่ชัดให้ใช้เพียงการอ่านหลักฐาน เก็บ REVIEW, audit และ preimage เพื่อกู้ต่อ การย้อน Worker รุ่นเดิมที่ปิด gate ขณะมีงานจองอาจปล่อยคิวทั้งไฟล์ ต้องยืนยันว่ารุ่นที่กู้ต่อคง gate และรองรับสิทธิ์ที่ยังค้างก่อนเปลี่ยน traffic

รอบ Production จะเริ่มหลัง UAT และการทบทวน release ของรุ่นนี้ผ่าน ด้วยขั้น ขนาดการส่ง และหลักฐานเช่นเดียวกัน ก่อนขยายงาน 29 รายการที่สร้างก่อน cutover ให้ตรวจประวัติแถวเก่าและจัดทำวิธีนำเข้าแท็บใหม่โดยเก็บประวัติการซิงก์เดิมไว้
