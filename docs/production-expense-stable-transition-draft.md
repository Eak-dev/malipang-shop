# Production expense projection candidate — not a release procedure

This branch extracts the legacy-writer stop control from #229 onto #224 and adds source revision/admission and projection-intent primitives. It does not route the production queue to a stable-identity writer, call Google with the new journal, enroll historic rows, or resolve held work. Enabling `EXPENSE_STABLE_PROJECTION_ENABLED` currently **holds** expense jobs in REVIEW; it does not turn on a working writer. Both feature flags default off.

The stop control applies only to code that contains and checks it. It holds new expense queue jobs in the existing outbox and rejects gate-aware daily and reconciliation writers; earlier Worker versions, already dispatched HTTP requests, Apps Script, other services and human editors can still write. Setting HOLD is not proof that they stopped. A cutover needs an independently verified exclusion and drain, including the RAW and detail tabs and any outstanding requests. The main queue also carries LINE and attendance work; do not pause it without an explicit impact, retention and recovery plan. Google Sheets does not provide a value compare-and-swap for these writes.

The source-revision migration adds triggers only to expense events, documents, links and document items. Affected expense IDs and integer revisions are stored, not a duplicate of customer descriptions or receipts. A revision changes even when source fields are later restored, and a deleted/reused expense ID becomes REVIEW. SQLite `INSERT OR REPLACE` may skip DELETE triggers. BEFORE INSERT collision checks cover the currently declared unique indexes, and the runtime checks their inventory, columns, collations and partial-index SQL; another unreviewed index or schema drift must hold the writer. BEFORE collision checks can also advance a revision when a duplicate is ultimately ignored. The main text quick-save path now suppresses an already-known message in its INSERT statement, but other writers, external SQL and unusual collision paths need audit. These triggers run in the **same transaction as business writes**: a D1/schema/constraint/resource error can make the original write fail. Revision exhaustion is intentionally fail-closed. The cost of documents linked to many expenses needs measurement against production-shaped data and actual D1; the small local SQLite benchmark is not a D1 performance result.

The collision checks also cover SQLite's internal `rowid`, including UPDATE OR REPLACE, independently of any Google Sheets row position. SQLite can report `NEW.rowid = -1` before an automatic INSERT as well as for an explicit `-1`. When a source table already has rowid `-1`, a normal insert can therefore conservatively advance an unrelated revision and, for an expense, hold the incoming identity in REVIEW. Removing that check would miss an explicit replacement and is unsafe. Before any rollout, verify these tables' rowid schema and arrange monitored detection and a reviewed recovery process for negative rowids and unexpected REVIEWs; do not silently renumber live records. A point-in-time read found no negative rowids in the four current production tables, which does not guarantee future state. These guards can themselves fail the underlying transaction on resource/constraint errors and cannot be represented as having no business impact.

Bootstrap must happen while all source writers are stopped. Migration atomicity and behavior with the actual D1 platform, failure/retry, restored backups and existing rows have not been established. Trigger-name presence is checked at journal dispatch, but that does not authenticate trigger SQL or prevent a privileged editor from changing the schema. Independently inspect the complete schema and migration before activating anything. No migration in this branch has been applied to production.

The intent repository requires a matching active cutover generation, gate HOLD, a post-watermark admission, a live outbox lease, a tracked current revision, no numeric legacy mapping, and no unresolved projection from any version. It records IN_FLIGHT/VERIFIED/REVIEW separately for DAILY, RAW and DETAIL and refuses to complete an outbox until all three match the same revision. An adapter-supplied digest is **not** independently verified provider evidence; a real adapter must authenticate, locate and validate stable identity, compare trusted preimages and all relevant postimages, and recheck its lease and revision immediately before dispatch. Historical items at or before the watermark, cancellations, missing identities, uncertain writes and legacy row hints remain held. There is no automatic timeout-based replay.

A document or item can change the source revision without changing the parent expense version. The candidate intent key now includes source revision, preserving previous evidence when the expense version is unchanged. The full RAW adapter and completion workflow still cannot process every such revision automatically; this remains a hold, not evidence of synchronization. Before release, design and implement a durable projection generation keyed to source revision (including an outbox/rescheduling path for document and item mutations). It must retain the old intent and provider evidence, refuse a new dispatch while any older attempt is IN_FLIGHT or REVIEW, and require explicit reconciliation of uncertain outcomes. Enqueue atomically with the relevant source change or provide an independently monitored durable scanner, and only mark each generation complete after all required projections have authenticated readback for that same source revision. Test duplicate notifications, multiple source revisions, worker crash and lost provider response, replay after completion, and version-unchanged edits. Recovery and operator alerts for held generations are not implemented yet.

The separately added generation observer is called only by the default-off cron scheduler. It records source revisions, including a review marker when source or revision evidence is missing, but its PENDING state does **not** authorize a Sheets write. It has no alert, generation-specific dispatch fence, completion, or operator recovery. Discovery can become stale immediately after its atomic read, and its REVIEW rows are not automatically released when a condition clears. The cursor and discoveries now commit in one batch and a local regression covers repeated changes to an earlier ID; this does not prove bounded fairness under an unbounded stream of new IDs. Discovery samples the latest revision visible at each scan and does not record intermediate revisions. It cannot detect a record if its event, revision and admission are all removed. Its full-source scan and sorting cost have not been measured on D1 and require bounds and operational alerts before any scheduling. It cannot claim complete rescheduling or an audit of all historical records. An actual consumer must recheck all eligibility atomically with a generation-scoped lease and must not treat absence of an observation as proof no work exists.

An additional D1 generation queue and cron hook are default-off and use the existing database, not a new Cloudflare Queue. The scheduler records pending and review work. A separately flagged, default-off consumer can claim one eligible generation per tick, but immediately holds it in REVIEW because the provider adapters and completion protocol are not ready; it never calls Google. When source advances, an unclaimed PENDING generation can be atomically marked SUPERSEDED if the current source and cutover remain eligible and no older outcome is unresolved; this lets the latest revision become PENDING. Other stale work and expired in-flight work are conservatively moved to REVIEW; they are not automatically retried or completed. In particular, a newer revision may remain in REVIEW until an operator reconciles the older generation. A lost claim acknowledgement remains IN_FLIGHT until review. No recovery UI, alert, bounded retention policy, validated operational reconciliation or provider writer exists. The canonical production projection guard now requires the generation worker flag and a supplied generation lease; it checks the exact generation-job token and unexpired lease in the same SQL statement as the existing source/cutover and sync-job lease checks. Both the generation and legacy sync-job leases are currently required and all completion is disabled. Migration 0030 is a not-yet-applied candidate whose key was changed to include revision; a database that already applied an older 0030 would require a separately reviewed migration, not a replay of the edited file. This does not prove Sheets identity or exclude other writers. A single materialization may create PENDING and REVIEW jobs for one expense; the claim must hold PENDING while a REVIEW exists. Do not enable either generation flag in production until the end-to-end path and its recovery have been reviewed and tested.

Before considering a release, build the production queue route and all three complete identity-based adapters, independently validate source and provider behavior and rollback, determine how to reconcile the existing PREPARED capacity expansion and historical outboxes, design auditable identity enrollment/recovery, and confirm source revision/trigger performance and privacy. A database restore must be reconciled with the corresponding Sheet state; rolling back code or removing revision triggers without that reconciliation destroys the basis for the source proof. A controlled release requires coordinated backup, independently verified all-writer exclusion, a safe handover of old worker versions, and post-release reconciliation. Until then, do not apply migrations, activate a cutover or enable the stable flag.
