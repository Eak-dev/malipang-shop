# Prototype: ตรวจรหัสรายการใน RAW และรายละเอียด (ยังไม่ใช่ระบบซิงก์ใหม่)

`buildLedgerUatAppendRequests` เป็นตัวทดลองสร้าง request สำหรับ EXPENSE/PERSONAL_USE บน UAT เท่านั้น โดยเลือกตำแหน่งต่อท้ายจาก snapshot ทั้งกริดและรวมการแทรกแถว ค่า และ metadata ใน batch เดียว มี reader ที่อ่านจาก Sheets โดยจำกัดขนาด 50,000 เซลล์รวมแถวใหม่ แต่ยังไม่มีผู้เรียกส่ง request และ snapshot ไม่ใช่หลักฐานว่าไม่มีคนแก้พร้อมกัน ต้องมี durable intent, การพิสูจน์การแยกสภาพแวดล้อม, source proof, provider readback, วิธีจัดการผลลัพธ์ไม่แน่ชัด และ cutover ที่กัน writer เก่าและการแก้พร้อมกันก่อนพิจารณาใช้งานจริง ห้าม retry เมื่อไม่ทราบผลเพียงเพราะหมดเวลา

สถานะ: ทดลองเท่านั้น ปิดโดยค่าเริ่มต้น ห้ามใช้เป็นหลักฐานสำหรับ deploy หรือบอกว่างานนี้แก้แถวผิดใน production แล้ว

มี helper `readRawSourceProof` และ `rawProjectionValuesMatch` สำหรับตรวจ source RAW/PERSONAL ทั้งแถวและเทียบค่าจาก provider ภายหลัง โดย source ของ expense และเอกสารอ่านใน D1 SELECT เดียว และเอกสารกำกวมต้องพักตรวจ helper เหล่านี้ยังไม่ต่อเข้าการเขียน production; fingerprint และค่าต้นทางอาจมีข้อมูลส่วนตัว ไม่ใช่วิธีปกปิดข้อมูล และการตรวจซ้ำยังไม่ใช่ immutable revision หรือ Sheets CAS

`inspectRawRecovery` เป็นตัวช่วยอ่านหลักฐานเมื่อผลเขียนไม่ชัดเจนเท่านั้น ผลทุกแบบยังเป็น REVIEW: ค่าที่ตรง preimage หรือ postimage ไม่ได้ยืนยันว่าใครเขียน ไม่อนุญาต retry, ปลด hold หรือปิดงานอัตโนมัติ; metadata ID ที่ตรวจต้องเป็น ID ของ intent และ provider observation ต้องสดและผ่านการยืนยันเอกลักษณ์

มี candidate reader สำหรับ RAW จริงซึ่งรับเฉพาะ metadata ID และชื่อชีตจาก configuration; ปิด flag โดยค่าเริ่มต้นและยังไม่มี route. ตัว full-RAW inner intent และ migration 0031 ใช้ canonical outer dispatch fence ใน SQL เดียวกับการจอง/ตรวจ intent; finish อ่าน provider แล้วตรวจครบทุกค่าและบันทึกหลักฐานที่ outer RAW verification ต้องตรงกัน กรณี D1 ตอบกลับไม่ชัดเจนให้ถือ UNKNOWN และพัก outer ไม่ retry อัตโนมัติ ได้ทดสอบ migrations 0029/0030/0031 ร่วมกันใน SQLite ภายในเครื่องแล้ว แต่ยังไม่มี enrollment หรือ production writer route และยังไม่มีหลักฐาน end-to-end กับ D1/Google จริง การตรวจนี้ไม่ป้องกัน editor หรือ writer เก่าพร้อมกัน. PERSONAL_USE ยังไม่พร้อมใช้งาน production

สำหรับรายการใหม่ มี reader/planner ที่อ่านทุกคอลัมน์ของ RAW ภายในขีดจำกัด และ candidate intent ใน migration 0033 ที่จอง metadata ID กับ sheet-wide lock ซึ่งไม่หมดอายุ การสูญหายของ D1 acknowledgement ไม่อนุญาตให้ process เดิมหรือ process ใหม่ส่งต่อโดยอัตโนมัติ มี candidate transport ที่บังคับ one-shot และอ่านกริด/ตรวจ fence หลัง OAuth แล้วอ่าน metadata และข้อมูลกลับ ทุกผลยังพัก REVIEW และไม่ปลด lock. ยังไม่มี production route, identity enrollment หรือ workflow ตรวจหลักฐานและปลด lock; ต้องผูก generation lease และตรวจระบบจริงก่อนใช้งาน. การตรวจนี้ไม่กันคน, source D1 หรือ writer เก่าเปลี่ยนข้อมูลขณะส่ง Google: หาก source เปลี่ยนระหว่าง request ชีตอาจเห็นข้อมูลล้าสมัยชั่วคราว แม้ readback จะพบและพักงาน

RAW identity reader/writer และ append planner ต้องเห็นหัวตารางครบตามลำดับทุกคอลัมน์ (expense 17 ช่อง, personal-use 15 ช่อง) ส่วน detail metadata witness ตรวจครบ 20 ช่อง หากมีการสลับหรือเปลี่ยนชื่อคอลัมน์ต้องหยุดตรวจ การอ่านหัวตารางในไฟล์จริงเป็นเพียงหลักฐาน ณ เวลาที่อ่าน ไม่ใช่การล็อกการแก้ไขคอลัมน์; detail ยังไม่มี trusted reader หรือ production route

มี candidate reader แบบปิดโดยค่าเริ่มต้นสำหรับ personal RAW ด้วย โดยจำกัด metadata ID และช่วงข้อมูลตามชื่อแท็บจาก configuration ตรวจ metadata ก่อนและหลังอ่านตาราง และตรวจหัวตาราง/identity เต็ม; ยังไม่ได้เชื่อม writer หรือ production route และผลอ่านเป็นหลักฐานเฉพาะขณะนั้น ไม่กันการเปลี่ยนข้อมูลภายหลัง

Migration candidate 0040 เพิ่ม identity intent สำหรับแถว personal ที่มี metadata และ baseline อยู่แล้ว; หลังอ่าน provider ครบทั้ง 15 ช่องและ source ซ้ำ จึงผูกผลเข้ากับ outer intent พร้อม generation/sync lease. กรณีคำตอบ D1 หลัง finish หายถือ UNKNOWN และพัก outer เมื่อทำได้. ยังไม่มี production route และต้องควบคุมการแก้ชีตพร้อมกันเพราะ Google ไม่มี CAS

Migration candidate 0041 เพิ่มทะเบียนเจ้าของ metadata ใน workbook เดียวกันและ trigger ปฏิเสธ ID ชนหรือ REPLACE ที่อาจลบ intent, ปฏิเสธการ reset REVIEW และปฏิเสธการลบ intent/registry เพื่อไม่ให้ผลไม่แน่ชัดหาย; personal enrollment มีข้อยกเว้นผ่าน admin recovery ที่ตรวจหลักฐานและ audit เท่านั้น; ข้อมูลเดิมที่ชนกันทำให้ migration ล้มแทนการเลือกเจ้าของเอง. Registry อนุญาตให้ expense append และ identity อ้างเจ้าของเดียวกันได้เพื่อรองรับการเปลี่ยนผ่าน แต่ **ไม่ได้พิสูจน์** ว่า provider เขียนสำเร็จหรืออนุญาต enrollment/VERIFIED. ต้องผูก workflow กับ provider readback และ lease รวมถึงตรวจ schema guard ในทุก writer ก่อนเปิด production; การตรวจชื่อ trigger ไม่ป้องกันผู้มีสิทธิ์แก้ SQL ฐานข้อมูลโดยตรง. การชน rowid บางกรณีอาจพักงานอย่างอนุรักษ์นิยม

การห้ามลบใน 0041 เป็นเพียง candidate ไม่ใช่นโยบาย retention ที่อนุมัติแล้ว: registry โตตามจำนวน metadata identity และ intent คงอยู่จนมีวิธีจัดการที่ผ่านการตรวจ. ก่อน production ต้องวัดจำนวน/ขนาดและอัตราเพิ่มจริง ประเมินต้นทุน/ขีดจำกัด กำหนดระยะเก็บและวิธี archive หรือกู้คืนที่รักษาหลักฐานผลไม่แน่ชัด รวมทั้งทดสอบ rollback ของ migration/schema และ worker ที่อาจไม่รู้จักข้อห้ามนี้; rollback code อย่างเดียวไม่ลบ trigger หรือย้อนข้อมูล D1/Sheets. ขณะนี้ยังไม่มีวิธีลบ/rollback ที่พิสูจน์ปลอดภัย จึงห้ามเปิด migration นี้

Personal enrollment candidate 0043 อ่านตารางจาก provider ตรวจ ID ไม่ซ้ำและค่าเทียบ D1, จอง metadata ภายใต้ D1 lock/generation lease และตรวจซ้ำหลัง OAuth ก่อนส่งคำขอเพิ่ม metadata ได้ครั้งเดียว; ไม่เขียนค่าหรือ note ในแถว. ผลทุกแบบยังพัก REVIEW รวมถึงอ่านกลับตรง และคำตอบขาดหรือผิดรูปถือ UNKNOWN ห้ามส่งซ้ำ. Admin recovery candidate 0044 อ่าน provider/D1 ซ้ำและอนุญาตปิดเฉพาะเคสที่ตรงภายใต้การยืนยันพักแก้และระบาย writer เก่า โดยไม่ส่ง Sheets ซ้ำ; ดู [runbook](personal-enrollment-recovery-runbook-th.md). การระบุแถวใช้ ID และค่าที่ตรง ไม่ต้องพิสูจน์ผู้สร้าง; snapshot ไม่ใช่ CAS และยังต้องควบคุมการย้าย/partial sort พร้อมกัน. Metadata แบบ PROJECT ของ Google project อื่นอาจมองไม่เห็น. Admin route ปิดโดยค่าเริ่มต้นและยังไม่ได้ deploy; ไม่แก้ historical pre-watermark และยังต้องทดสอบ recovery สำหรับเปิดจริง

`auditLegacyExpenseRawEnrollment` ใช้ตรวจว่าภาพข้อมูลที่ส่งเข้ามามี ID เดียวและค่า RAW ทั้งแถวตรง source หรือไม่ โดยไม่คืนเลขแถว ทุกผลเป็น REVIEW; `SINGLE_MATCH` บอกเพียงว่าตรงกับ snapshot ที่ caller ส่งมา ไม่ยืนยันว่าอ่านจาก Google จริงหรืออนุญาตผูก metadata. การลงทะเบียนแถวเก่าจริงยังไม่มีเส้นทางและต้องมีหลักฐาน identity, trusted read, durable intent และการกันการแก้พร้อมกัน

มี migration candidate 0035 สำหรับ source revision/admission ของ PERSONAL_USE ใน D1 เดิม และปรับ INSERT ของ service เพื่อไม่เพิ่ม revision เมื่อ webhook เดิมส่งซ้ำ; migration 0037 เพิ่ม outer intent แบบปิดโดยค่าเริ่มต้น ตรวจ revision, admission, schema, lease, cutover และ gate โดยไม่จำเลขแถว และรองรับเฉพาะรายการ CONFIRMED; ยังไม่มี route หรือวิธีจัดการรายการ CANCELLED. ทั้งสอง migration ยังไม่ apply. Trigger ทำงานใน transaction ของรายการส่วนตัวและอาจทำให้ธุรกรรมล้มเพื่อรักษาหลักฐาน revision จึงต้องตรวจภาระและผลกระทบจริง, schema/index/foreign-key integrity รวมถึง drain source writer ระหว่างติดตั้งก่อนพิจารณา production. REPLACE/rowid บางกรณีอาจเพิ่ม revision อย่างอนุรักษ์นิยมแม้ข้อมูลธุรกิจไม่เปลี่ยน

Personal outer intent เป็นเพียงโครงป้องกัน migration candidate 0038 เพิ่มตัวค้น revision แบบแบ่งรอบและบันทึก observation ใน D1 เดิม และ 0039 เพิ่ม generation queue/lease ซึ่งยังปิดเป็นค่าเริ่มต้นและไม่มี route: PENDING ไม่อนุญาตให้เขียนชีต, consumer พัก REVIEW เสมอ และ lease หมดอายุหรือผลไม่แน่ชัดห้าม retry. Outer guard บังคับ lease ของ generation และ sync job พร้อมกัน แต่ยังไม่มีวิธีเชื่อม generation ใหม่เข้ากับ sync job เดิมที่ COMPLETED อย่างปลอดภัย. ตาม service ปัจจุบัน การยกเลิกร่างไม่สร้างงานชีต ส่วน UNDO หลังยืนยันสร้างงานอัปเดตสถานะ CANCELLED ของรายการเดิม; discovery จึงพัก CANCELLED เป็น REVIEW จนพิสูจน์ประวัติและตัวตนแถวเดิมได้ โดยไม่สร้างหรือลบแถวเอง

มี candidate gate ปิด writer เก่าของ PERSONAL_USE: durable gate HOLD หรือ cutover ใด ๆ มีผลแม้ config ปิด/ไม่ตั้ง; หลังติดตั้ง schema ต้องมี gate OPEN ตรง workbook/แท็บจึงใช้ writer เดิมได้ และตรวจซ้ำก่อนจัดสรรแถว หลัง OAuth และใน SQL ต่อ lease. ก่อน migration ใช้โหมดเดิมได้เฉพาะเมื่อ `d1_migrations` ตรง canonical manifest ที่ตรวจแล้ว ไม่มี version 0037 ขึ้นไปและไม่มีตาราง gate/cutover; ชื่อผิด version ซ้ำ migration ที่คาดหวังขาด schema ขัดกันหรือ DB error ให้หยุด. หมายเลขที่จงใจข้ามใน manifest ไม่ถือว่าขาด แต่ release ใหม่ต้องทบทวน manifest; ledger ไม่กันการลบ/restore จึงต้องเทียบประวัติ release แยกก่อน cutover. Bootstrap ใน release candidate จำกัดเป็นการอ่านรายชื่อแท็บเท่านั้น ไม่สร้างแท็บ ไม่เขียนหัวตาราง และไม่แก้หน้า 04; endpoint ตอบ HTTP 409 และ `ok: false` พร้อม `READ_ONLY`, `headersVerified: false`, `requiresManualSetup: true` และ `setupComplete: false` แม้ชื่อแท็บครบ ผู้ดูแลต้องสร้างแท็บที่ขาดและตรวจหัวตารางเอง ผลกระทบนี้ครอบคลุม bootstrap ทุกแท็บ การตั้งค่าอัตโนมัติยังไม่พร้อมจนกว่าจะมี durable intent และวิธีกู้ผลที่ไม่แน่ชัด รวมทั้งประสานการแก้ชีตระหว่างเขียน

ยังไม่มี stable queue route จึงห้ามเปิด stable flag นี้ใน production เพราะจะพักงานส่วนตัว; gate หยุด Worker รุ่นเก่าที่ไม่ได้รหัสนี้หรือ request ที่ส่งไปแล้วไม่ได้ และยังมีช่องเวลาหลังตรวจ D1 ก่อนส่ง Google ต้องระบาย writer/requests ก่อน migration และ cutover. D1 row cache ที่ถูกจัดสรรก่อน gate ปิดอาจยังค้าง ต้องตรวจ ไม่ใช่หลักฐานตัวตน

Historical enrollment candidate สำหรับรายการส่วนตัวเดือนตุลาคมใช้ ID ที่ไม่ซ้ำ ตรวจค่า owned fields ทั้งหมด และจอง metadata/ล็อกแท็บร่วมใน D1 โดยไม่เก็บเลขแถว ก่อนส่ง metadata อ่านชีตและตรวจ source อีกครั้ง ส่งได้ครั้งเดียว และเก็บผลที่ไม่ชัดไว้ตรวจ ไม่ replay. Fast-path candidate ลง receipt, stable identity, audit และปลดล็อกใน D1 batch เดียวเฉพาะเมื่อ Google ตอบรับและอ่านกลับตรงครบ ส่วนผลที่ไม่ชัดใช้ quarantine และ admin recovery หลังเวลารอขั้นต่ำ โดยไม่ส่งซ้ำ การกลับมาซิงก์ revision ใหม่ยังปิดเป็นค่าเริ่มต้นและตรวจ verified identity กับ registry ไม่ใช้ row cache. Admin dispatch route candidate ปิดเป็นค่าเริ่มต้น ต้องผ่าน bearer authentication และเปิด flag แยก การกู้กรณี metadata ติดผิดแถวหรือไม่ปรากฏยังไม่ครบ ห้ามเปิด flag หรือ deploy ก่อนผ่านการตรวจสอบและวางแผน rollout; การยืนยันพักแก้ชีต ระบาย writer และรอ request เก่า เป็นคำยืนยันของผู้ดูแล ไม่ใช่การล็อก Google Sheets

Outer guard ปฏิเสธ source revision ที่ต่ำกว่า observation หรืองาน generation ที่เคยบันทึกไว้ใน workbook เดียวกันแม้คนละ generation แต่ไม่สามารถพิสูจน์ revision ที่ไม่เคยถูกสังเกตหรือหลักฐานที่ถูก restore หายไปทั้งหมดได้

ยังต้องมีวิธี recovery ที่ตรวจ provider เมื่อผลไม่แน่ชัด และการเชื่อม writer กับ provider readback, enrollment, การกั้น writer เดิมและ editor ระหว่างเขียน รวมถึงทดสอบ D1/Google จริงก่อนเปิด route. ห้ามตีความว่ารายการ personal ซิงก์ครบจากการทดสอบนี้. สถานะ intent หรือ D1 lock ไม่ใช่ Google Sheets CAS และไม่ป้องกันเจ้าของไฟล์ที่ข้าม protection ได้

เมื่อ `SHEETS_LEDGER_IDENTITY_INSPECTION=true` งาน EXPENSE/PERSONAL_USE และ purchase detail จะอ่านรหัสในชีตปัจจุบัน โดยไม่อ่าน `sheet_row_index` และพักเป็น REVIEW ก่อนจอง/เขียนแถวเสมอ การตรวจพบหนึ่งรายการไม่ได้อนุญาตเขียน เพราะผู้ใช้สามารถย้าย ลบ หรือคัดลอกแถวระหว่างอ่านกับเขียนได้ เมื่อไม่ตั้งค่า flag เส้นทางเดิมไม่เปลี่ยนและยังมีความเสี่ยงเดิม

RAW ใช้ Expense_ID และ Personal_Use_ID ในคอลัมน์ A; purchase detail ใช้ Purchase_Item_ID คอลัมน์ A ร่วม Expense_ID คอลัมน์ B. Snapshot ต้องครอบคลุมขนาด grid จริง ไม่เกิน 10,000 แถว และหัวตารางต้องตรง; ไม่พบ, พบซ้ำ, ข้อมูลไม่ครบ, grid ใหญ่เกินหรืออ่านไม่ได้ ต้อง REVIEW และไม่บันทึกข้อมูลส่วนตัวลงข้อความเหตุผล. ค่าตรงเพียงรายการเดียวเป็นเพียงหลักฐาน ณ เวลาที่อ่าน ไม่ใช่การรับรองเอกลักษณ์หรืออนุญาตแก้ไข.

ก่อนเปลี่ยนเป็นระบบใช้งานจริง ต้องมีวิธีเขียนโดยอ้างอิง identity ที่เคลื่อนตามแถวแทน A1 snapshot, จัดการ sort เฉพาะคอลัมน์/duplicate/copy, race กับผู้ใช้และ worker เก่า, การค้นหาเมื่อข้อมูลย้าย/หาย, operation ที่ผลลัพธ์ไม่แน่ชัด, safe append และการ recover โดยไม่สร้างรายการซ้ำ พร้อมทดสอบ Google Sheets จริงบนสำเนาและแผน cutover/reconcile. ระบบจริงยังไม่มีการเปิด flag หรือแก้ configuration.

มีต้นแบบ request `values.batchUpdateByDataFilter` ที่ชี้ด้วย metadata ID เฉพาะแถวแทนเลขแถว โดยรักษาคอลัมน์ ID และระบุเฉพาะ field ที่ตั้งใจแก้: ทุก field ต้องตรง preimage ที่เชื่อถือได้ และจะพักหากมีสูตร, note, validation, preimage ไม่ครบหรือมีการแก้โดยผู้ใช้ การยกเลิก detail แก้เฉพาะสถานะ/เวลา ตัวทดลองยัง **ไม่เชื่อมกับเส้นทางซิงก์**, ถูกปิดด้วยค่าเริ่มต้น, ใช้ได้เฉพาะ `RUNTIME_MODE=shadow` ที่ระบุ workbook UAT และ production ต่างกัน, ไม่มีขั้นตอนติด metadata ให้รายการเดิมหรือเพิ่มรายการใหม่ และทดสอบกับ mock ไม่ใช่ Google Sheets จริง. การตั้ง ID ใน environment เป็นเพียง assertion ไม่พิสูจน์ตัว workbook หรือแยก writer เอง ต้องตรวจด้วยหลักฐานภายนอก Metadata จะตามการย้ายแถวทั้งแถว แต่ผู้ใช้ยังสามารถ sort เฉพาะบางคอลัมน์หลังตรวจข้อมูลทำให้ข้อมูลกับ metadata ไม่ตรงกันได้. ห้ามเปิด `SHEETS_LEDGER_ANCHORED_WRITE_PROTOTYPE` ใน production จนมี cutover ที่กัน writer เก่าและมีวิธีตรวจสอบ identity ที่รับมือ concurrent edits ได้จริง.

Migration ทดลอง 0025 เพิ่ม journal ต่อ workbook/แท็บ/entity เพื่อเก็บ metadata ID, source version, SHA-256 ของค่าช่องที่ตรวจ และสถานะ VERIFIED/IN_FLIGHT/REVIEW โดยไม่เก็บเลขแถว และไม่เก็บสำเนา message ID, trace ID หรือ evidence reference. Digest ของค่าที่เดาได้ง่ายยังเดาได้และไม่ใช่การเข้ารหัส D1 ต้องคงเป็น private. Journal ตรวจ snapshot ต้นทางก่อนเริ่มและก่อนจบ; detail ตรวจ parent, document, item, sibling count/ยอดรวม/ลำดับแรกด้วย แต่ coordinator ยังต้องตรวจ item ทั้งชุดก่อนปิดงาน. ฟังก์ชัน shadow ต้องพบ marker ฐาน UAT แยกต่างหากที่ migration นี้ไม่สร้าง และไม่เปิดทาง enrollment, retry อัตโนมัติหรือ production. โค้ดยังไม่ต่อเข้ากับงานซิงก์จริง; caller ต้องอ่าน journal ที่เชื่อถือได้และยืนยัน provider postimage, ไม่สร้าง hash จากค่าที่เพิ่งอ่านแล้วอ้างว่าเป็น baseline เดิม.
# Google reader UAT experiment

`createLedgerGoogleUatProbe` reads the row metadata, a bounded full-grid snapshot and the metadata again through an authenticated Sheets client. It is shadow-only, requires distinct asserted UAT and production IDs, and is not routed into live sync. It conservatively holds an entire sheet with any protected range or merge. Formula identities, duplicate/moved identities, ambiguous grid shape and mismatched metadata hold. Mock transport tests do not prove Google's response shape or exclusive access. The metadata-before/after check cannot detect every concurrent edit, partial sort, or ABA move; it is not a Sheets compare-and-swap. A real provider test, trusted isolation and complete cutover remain prerequisites.
