# Synthetic expense workflow UAT — isolated test only

This branch combines experimental daily and RAW CORE adapters. The endpoint is not available in production, is not connected to the production queue, and does not support a complete expense projection. The owner has authorized eventual production rollout, but this fixture is not a release candidate.

The endpoint `POST /admin/uat/expense-projection-workflow` requires the existing admin authentication, shadow mode and both daily and ledger QA guards. It accepts no expense data or adapter configuration in the request; the single synthetic expense ID comes from server configuration. The UAT workbook ID must be distinct from independently verified production workbook IDs and both QA-only marker tables must exist in the independently verified synthetic database. Configured strings and `EXCLUSIVE_EDITORS=true` are assertions, not independent proof of isolation. Do not use a production Worker version, D1 binding, workbook, queue or credentials arrangement that can mutate production resources.

Prepare one disposable workbook and D1 fixture with (1) the active synthetic source boundary, (2) a confirmed test expense and pre-existing PENDING outbox, (3) a verified daily stable identity for the prior version, and (4) a verified RAW CORE metadata identity and baseline for the prior version. The current expense version must be newer than the enrolled RAW CORE version. Daily and RAW rows must have correct formulas, identities and metadata. There is currently no automated safe enrollment, no new RAW append, and no DETAIL adapter. Do not infer enrollment from matching names or amounts. Do not place personal data in the fixture. Source snapshots are plaintext in the synthetic D1 journal; the 64 KiB cap is a prototype bound, not a production retention decision.

The endpoint claims only an existing outbox. It checks the source boundary and source snapshot and invokes the daily adapter; then it attempts a metadata-anchored update of already-enrolled RAW CORE. Each adapter must check the shared projection lease, source and boundary immediately before its Google mutation. If RAW CORE succeeds, it remains PARTIAL because document and submitter cells are not covered and DETAIL is unavailable. The job must therefore return HTTP 409 `REVIEW`; the outbox is REVIEW and no DETAIL write is attempted. A 409 alone does not prove which step succeeded. The internal daily digest is only a marker after that adapter's own readback, not a digest of Google data.

Inspect only the isolated fixture's journal states and provider readbacks, without exposing tokens, private keys or row contents. Confirm the whole job was never marked COMPLETED, the expected monthly totals and next month are unchanged apart from the intended fixture, and no production resources were touched. If a response or mutation is uncertain, preserve the outbox, projection journals and fixture; do not replay or reset them. Cleanup can occur only after an independently reviewed outcome. A missing or mismatched QA marker must fail before the outbox is claimed or Google is called.

Authenticated Google `values:batchUpdateByDataFilter`, the combined worker route, live D1 behavior and native formula/subtotal results for this exact integration commit have not yet been tested end to end. Sheets does not supply compare-and-swap for these writes; preflight and postcheck cannot prevent another editor or old writer overwriting a cell between requests. A real cutover still needs enforced exclusive editing, old-writer drainage, legacy identity evidence, all projection adapters and a reviewed recovery workflow.
