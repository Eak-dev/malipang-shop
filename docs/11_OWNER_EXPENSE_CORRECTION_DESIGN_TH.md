# ออกแบบ: เจ้าของแก้รายการที่พนักงานส่งผ่าน LINE

สถานะ: แบบร่างสำหรับพัฒนาและทดสอบ ยังไม่ได้เปิดใช้จริง

## เป้าหมายและขอบเขต

เจ้าของที่ยืนยันตัวตนแล้วค้นหาและแก้รายการค่าใช้จ่ายที่ตนหรือผู้ใช้คนอื่นส่งมาได้ ทั้งรายการที่กำลังรอยืนยันและรายการที่บันทึกแล้ว โดยแก้ได้เฉพาะ **หมวด รายละเอียดรายการ ยอดชำระสุทธิ วันที่ชำระ และช่องทาง/แหล่งเงิน** ตามที่เจ้าของระบุ การแก้รายการย่อยในใบเสร็จ การลบหลักฐาน การยกเลิกค่าใช้จ่าย และการสร้างรายการใหม่ไม่อยู่ในขอบเขตนี้

ข้อมูลในภาพ เอกสารต้นฉบับ เลขอ้างอิง และรายการย่อยต้องคงไว้ เจ้าของเห็นทั้งข้อมูลที่อ่านจากหลักฐานและค่าปัจจุบันที่มีผล โดยแสดงชัดว่าแต่ละค่าเจ้าของแก้เมื่อใด ไม่เขียนค่าที่เจ้าของแก้ทับข้อมูลดิบของภาพ และไม่ถือว่าแก้หลักฐานการชำระเงินด้วย

## ขั้นตอนใน LINE

1. เจ้าของพิมพ์ `แก้ไขค่าใช้จ่าย` แล้วค้นหาด้วยวันที่ ชื่อร้าน/รายละเอียด หรือยอด กำหนดช่วงและแบ่งหน้า แสดงผลเท่าที่จำเป็น ไม่ค้นจากชื่อผู้ส่งอย่างเดียว
2. รายการแต่ละใบแสดงวันที่ ยอด รายละเอียด หมวด ช่องทางชำระ สถานะ และผู้ส่งเท่าที่เจ้าของจำเป็นต้องตรวจ เลือกจากรายการที่มีรหัสเฉพาะ ห้ามเดารายการจากข้อความหรือยอดที่ซ้ำกัน
3. กด `แก้ไข` เลือกช่องที่ต้องการ ระบบแสดงค่าเดิมและรับค่าใหม่ผ่านปุ่มหรือข้อความที่ระบุชัด ค่าที่กรอกเก็บในร่างของเจ้าของ ยังไม่เปลี่ยนรายการจริงหรือรายงาน
4. แสดงหน้าสรุปเดิม → ใหม่ และผลกระทบต่อเดือนและบัตรหากมี เจ้าของกด `ยืนยันการแก้ไข` หรือ `ยกเลิก` ระบบตรวจตัวตน สิทธิ์ สถานะ และเวอร์ชันซ้ำ ณ เวลากด หากข้อมูลเปลี่ยน ให้เปิดรายการใหม่ ไม่ใช้คำยืนยันเก่า
5. เมื่อบันทึกสำเร็จ แจ้งว่า `บันทึกแล้ว กำลังปรับข้อมูลที่เกี่ยวข้อง` และแสดงสถานะซิงก์จนเสร็จ หากซิงก์ไม่สำเร็จ แจ้งให้ตรวจและลองซิงก์ต่อโดยไม่บันทึกรายการซ้ำ

รายงานและชีตรับข้อมูลหลังเจ้าของยืนยันเท่านั้น ไม่เปิด Dropdown ที่เปลี่ยนคอลัมน์หมวดซึ่งสูตรรายงานอ่านโดยตรงก่อนอนุมัติ ต้องป้องกันการแก้คอลัมน์ที่มีผลต่อรายงานโดยผู้ไม่มีสิทธิ์ และคงสิทธิ์ให้ Worker เขียนได้ โดยทดสอบสิทธิ์จริงในสำเนาก่อนเปลี่ยนชีตใช้งาน

## กติกาเมื่อแก้แต่ละช่อง

| ช่อง | ตรวจและผลต่อระบบ |
| --- | --- |
| หมวด | เลือกจากหมวดที่ระบบรองรับ เก็บเดิมและใหม่ ปรับหมวดสรุปและข้อมูลรายละเอียดที่เกี่ยวข้องตามกติกาหมวดที่ได้รับอนุมัติ |
| รายละเอียด | จำกัดความยาวและแสดงก่อนยืนยัน เปลี่ยนคำอธิบายของรายการค่าใช้จ่าย ไม่เปลี่ยนชื่อสินค้าในหลักฐานโดยอัตโนมัติ |
| ยอด | รับยอดสุทธิเป็นบาท/สตางค์ที่มากกว่าศูนย์ แสดงผลต่างเดิมและใหม่ ไม่เปลี่ยนยอดที่อ่านจากภาพหรือกระจายผลต่างลงสินค้าย่อยเอง หากใบเสร็จมีหลายรายการและผลต่อรายงานย่อยยังระบุไม่ได้ ให้ค้างตรวจแทนการเดา |
| วันที่ชำระ | ตรวจวันที่จริงและแสดงปีให้ชัด คำนวณเดือนลงชีตตามกติกาปัจจุบันของช่องทางชำระ ไม่แทนวันสั่งซื้อเป็นวันชำระ |
| ช่องทาง/แหล่งเงิน | เลือกจากรายการที่รองรับ ตรวจทั้งบัตร/วิธีชำระและแหล่งเงิน แสดงเดือนและคอลัมน์ลงบัญชีก่อนยืนยัน |

หากแก้ยอด วันที่ หรือช่องทางแล้วกระทบเดือนที่ปิดบัญชี ต้องแสดงผลกระทบและหยุดรอตรวจตามนโยบายปิดเดือนที่ตรวจสอบได้ ห้ามสมมติว่ามีสิทธิ์เปิดเดือนหรือปรับยอดปิดย้อนหลังโดยอัตโนมัติ หากยังไม่มีวิธีตรวจสถานะปิดเดือนที่เชื่อถือได้ ให้ทำเป็นข้อจำกัดก่อนเปิดใช้ช่องเหล่านี้จริง

## การรักษาความถูกต้อง

- ใช้ `expense_id` และรหัสเอกสารที่สัมพันธ์กัน รวมทั้งรหัสแถวที่ตรวจยืนยันแล้ว ไม่ใช้เลขแถวจาก `sheet_row_index` เพียงอย่างเดียว เพราะการแทรกแถวทำให้ตำแหน่งคลาดเคลื่อนได้
- จำกัดสิทธิ์ให้ OWNER ที่ active มีบทบาทระดับองค์กรและมี LINE binding ที่ยืนยันแล้ว ตรวจซ้ำในธุรกรรมที่ยืนยัน การปลอม postback รหัสรายการ หรือกดจากเมนูเก่าไม่ให้เปลี่ยนข้อมูล
- สร้างร่างแก้ไขที่ผูกเจ้าของ รายการ เวอร์ชันและ snapshot ของทุกช่องที่เกี่ยวข้อง พร้อมเวลาหมดอายุ โดยค่าที่เกี่ยวข้องของรายการรอยืนยันต้องเปรียบเทียบกับฐานข้อมูลจริงด้วย ไม่สมมติว่าเวอร์ชันเปลี่ยนทุกครั้ง
- ในธุรกรรมฐานข้อมูลเดียว ตรวจ snapshot แล้วบันทึกค่าใหม่ ประวัติก่อน/หลัง ผู้อนุมัติ เหตุผลและเวลา เพิ่มเวอร์ชัน และสร้างงานซิงก์ถาวร การตอบ LINE หรือส่งคิวล้มเหลวต้องไม่ทำซ้ำธุรกรรม
- รักษาใบเสร็จเดิมและการเชื่อมรายการไว้ ตรวจยอดย่อยและยอดเอกสารกับยอดใหม่ แสดงความต่างให้ตรวจ ไม่เขียนข้อมูลที่มาจากภาพทับด้วยข้อมูลที่เจ้าของระบุ
- การแก้วันที่หรือบัตรอาจย้ายข้ามบล็อกเดือนใน `รายวัน` ระบบต้องตรวจตัวตนแถวเดิม สำรองปลายทางที่ถูกต้อง ย้ายอย่างทนต่อการลองซ้ำและตรวจว่าเหลือรายการเงินออกหนึ่งแถวเท่านั้น ห้ามเขียนเดือนใหม่ลงแถวเดิมโดยไม่ตรวจบล็อก และห้ามล้างแถวที่ระบุไม่แน่ชัด
- ใช้คิวพร้อม version fence, idempotency และ recovery แยกจากคำตอบ LINE ติดตาม D1, ชีตรายวัน, ข้อมูลดิบ, รายการย่อย และรายงาน ข้อมูลที่ยังซิงก์ไม่ครบต้องมองเห็นได้ ห้ามแจ้งว่าเสร็จสมบูรณ์ก่อนตรวจผล
- แถวประวัติที่ไม่มี expense ใน D1 หรือจับคู่กับหลักฐาน/แถวได้ไม่แน่นอน ให้แสดง `ต้องตรวจเพิ่มเติม` ไม่สร้างหรือเปลี่ยนรายการเงินจริงโดยเดา

## ข้อค้นพบจากระบบปัจจุบันที่ต้องแก้ก่อนใช้งาน

1. การแก้ผ่าน `expense_set_category` และช่องอื่นใน flow เดิมจำกัด `WAITING_CONFIRM` และผูก `line_user_id` ของผู้ส่ง เจ้าของจึงยังแก้รายการที่คนอื่นส่งหรือรายการที่บันทึกแล้วด้วยเส้นทางนี้ไม่ได้
2. การลง `รายวัน` เดิมใช้ `sheet_row_index` และเมื่อพบแถวเก่าอาจใช้แถวนั้นต่อ แม้วันหรือบัตรใหม่ทำให้เดือนปลายทางเปลี่ยน ต้องออกแบบการย้ายและยืนยันตัวตนแถวก่อนเปิดแก้วัน/บัตร
3. ชีต `97_EXPENSE_CLEAN` อ่านหมวด `รายวัน!V` โดยตรงสำหรับข้อมูลเก่าบางช่วง ทดลองในสำเนาแล้วรายงานเปลี่ยนก่อนอนุมัติ หากใช้คอลัมน์เดิมเป็นช่องขอแก้ จึงต้องให้ LINE เป็นทางเสนอและป้องกันช่องรายงาน
4. `รายละเอียดการซื้อ` คำนวณผลต่างยอดเอกสารกับยอดสินค้ารวมจากข้อมูลปัจจุบัน และรายงานบางส่วนใช้งานยอดนี้ ต้องทดสอบผลต่อยอดและหมวดย่อยจริงก่อนเปิดแก้ยอด ไม่ถือว่าการเปลี่ยนเฉพาะยอดสรุปทำให้รายงานทั้งหมดถูกต้องโดยอัตโนมัติ
5. ข้อเสนอ Dropdown ใน PR #220 ยังไม่พร้อมใช้งาน ต้องไม่นำไปเปิดใช้โดยไม่แก้ประเด็นข้างต้น

## การทดสอบและการเปิดใช้

ทดสอบ owner/พนักงาน/สิทธิ์ที่ถูกเพิกถอน, รายการของผู้ส่งอื่น, รอยืนยัน/บันทึกแล้ว, ข้อมูลซ้ำ, การกดซ้ำ, ร่างหมดอายุ, แก้พร้อมกัน, วันที่ผิด, ยอดผิด, ตัดรอบบัตรข้ามเดือน/ปี, ไม่มีแถวว่าง, แทรกแถว, ใบเสร็จหลายรายการ, หมวด/ยอดรายงานก่อนและหลังยืนยัน, เดือนที่ปิดแล้ว, LINE และ Sheets ตอบล้มเหลว และคิวทำซ้ำ ต้องตรวจจำนวนรายการ ยอดรวม และความสัมพันธ์ข้อมูลก่อน/หลัง ไม่ให้เกิดรายการซ้ำหรือสูญหาย

เริ่มจากสภาพแวดล้อมทดสอบที่มีข้อมูลจำลองและ LINE callback แยก ตรวจสิทธิ์ของชีตกับเจ้าของ พนักงาน และ service account จากนั้นใช้ feature flag ปิดเป็นค่าเริ่มต้น เตรียม migration สำรองและกู้คืน ทดสอบ UAT พร้อมแผนย้อนกลับ และขออนุมัติ Production Change แยกก่อนเปิดใช้งานจริง
