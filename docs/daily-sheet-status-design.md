# สัญญาณพักแก้ไขรายวัน — แบบเสนอ ยังไม่เปิดใช้

## เป้าหมายและตำแหน่งเริ่มต้น

แสดงช่วงที่ระบบกำลังเตรียมหรือเขียนข้อมูล เพื่อให้ผู้ใช้พักการแก้ไขชั่วคราวโดยไม่ต้องกดยืนยันทุกครั้ง เมื่อสถานะไม่ทราบหรือเวลาเก่า ให้ถือว่า **งดแก้และตรวจสอบ** สัญญาณนี้อาศัยความร่วมมือ ไม่ได้ล็อกเจ้าของไฟล์หรือพิสูจน์ว่าไม่มีคนแก้

จากการอ่านครั้งหนึ่ง B1/C1 ของชีตรายวันไม่มีค่าหรือ note/data validation ที่ส่งคืน และเลือกแยกเป็นเซลล์เดี่ยวได้ B1 ตั้ง Arial 11 ส่วน C1 ตั้ง Arial 11 และจัดกลาง ทั้งคู่พื้นขาว ชิดล่าง และ overflow; A1 มี note เดิมจึงไม่ใช้ ข้อมูลอาจเปลี่ยนได้ ต้องตรวจใหม่ทันทีในช่วงติดตั้งจริง แผง Named ranges และ Protected sheets and ranges ไม่แสดงรายการขณะตรวจ การอ่านสูตรทั้งไฟล์แบบแบ่งช่วงไม่พบ direct reference ที่ตรวจได้มายัง A1:C3; INDIRECT ทั้ง 195 สูตรที่พบมีปลายทางระบุ prefix SRC_TEAM_ หรือ SRC_ACTUAL_ ไม่ใช่รายวัน ผลนี้ไม่ใช่หลักฐานว่าระบบภายนอกทุกระบบไม่อ้างอิง

B1/C1 รวมกันแคบและคอลัมน์ยังไม่ได้ตรึง จึงหายจากจอเมื่อเลื่อนแนวนอน แนวทางที่เสนอคือประเมินตรึง A:C ซึ่งจากภาพ desktop ที่ zoom 100% กว้างรวมประมาณ 160px; หากนำไปเทียบหน้าจอ 375px โดยสมมติสเกลเท่ากันจะกินพื้นที่ราว 43% จึงต้องทดสอบหน้าจอมือถือจริงก่อน การเลือก C1:D4464 ใน UI ไม่แสดง Unmerge และยังคงขอบ C:D; การเลือกบางส่วนของ F1:J1 ที่ทราบว่ารวมเซลล์ทำให้ UI ขยาย selection และเปิด Unmerge จึงเป็นหลักฐานเบื้องต้นว่าไม่พบ merge ตัดขอบ C/D ใน snapshot นี้ แต่ไม่ใช่รายการ merge ดิบจาก API ต้องตรวจอีกครั้งก่อนตั้งจริง

แถว 1 ช่อง D/E/F/K/S/T/U/V/W มีค่า และหลายช่องมี note โดย F1:J1 รวมเซลล์จริง ช่องที่ดูว่างในช่วงนี้จึงไม่ใช่พื้นที่ overflow อิสระ; grid มีถึง Y เท่านั้น ไม่อ้างว่ามี Z1 ให้ใช้ B1/C1 ต้องพิสูจน์ขนาดข้อความก่อนติดตั้ง ห้ามเปลี่ยน width/merge/format โดยไม่สำรองและตรวจผลกระทบ

หากเลือกตรึง ให้สำรอง gridProperties.frozenColumnCount เดิมและขอบเขต merge/ขนาดคอลัมน์ แล้วตั้งค่าเฉพาะ property ดังกล่าวหลังตรวจผล; ก่อน rollback ต้องตรวจว่า property ยังเป็นค่าที่ระบบตั้งและไม่มีการแก้ภายหลัง การตรึงเป็นค่าการแสดงผล ไม่ใช่เลขแถวธุรกรรม ทุกครั้งที่ตรวจสถานะต้อง resolve named range สดและยืนยันว่าป้ายยังอยู่ในบริเวณ frozen ไม่สมมติว่า B/C ไม่เคยเลื่อน

## ตัวตนของช่องและข้อมูลสำรอง

1. ติดตั้งครั้งเดียวเฉพาะเมื่อ release gate ผ่านและตรวจ B1/C1 สด: ใช้ named range สองชื่อที่ไม่ซ้ำกับชื่อชีต ผูกหนึ่งช่องต่อชื่อ และเก็บ **namedRangeId**/spreadsheet ID/sheet ID ใน D1 อย่างจำกัดสิทธิ์ ตำแหน่ง B1/C1 ใช้เฉพาะตอนติดตั้ง ไม่ใช่เลขแถวที่นำไปจำสำหรับการเขียนครั้งต่อไป
2. ทุกครั้งที่อ่าน/เขียน ค้น namedRangeId สดและยืนยันว่าชื่อยังไม่ชน, เป็นช่องเดี่ยวสองช่องต่างกัน, อยู่ในชีตที่ถูกต้องและยังอยู่ในส่วนหัวที่มองเห็นได้; ตรวจ merge/protection, ค่า, สูตร, note, validation และรูปแบบตามสิทธิ์ที่เข้าถึงได้ หากสูญหาย ซ้ำ เปลี่ยนปลายทาง หรือพิสูจน์ไม่ได้ ให้ REVIEW ไม่เดาจากพิกัดเก่า
3. ก่อนติดตั้ง สำรอง CellData ของแต่ละช่องแยกกัน รวม userEnteredValue, userEnteredFormat, note, dataValidation, textFormatRuns และข้อมูล rich content ที่ API รองรับ พร้อม field-presence, named-range identity, merge/protection, ขนาดแถว/คอลัมน์ที่อาจถูกปรับ, เวลาที่อ่าน และภาพอ้างอิง effectiveFormat เป็นข้อมูลตรวจ ไม่ใช้เขียนคืนแทน userEnteredFormat ตกลงที่เก็บ สิทธิ์เข้าถึง และระยะเก็บก่อนทำจริง
4. หลังติดตั้ง ทุก update เปรียบเทียบ preimage กับ postimage ครั้งก่อนที่ระบบเป็นเจ้าของ; ถ้าคนเปลี่ยนค่า สูตร note หรือ format หรือผล request ไม่แน่ชัด ให้ REVIEW ไม่เขียนทับและไม่คืนค่าอัตโนมัติ การกู้คืนตรวจ identity สดและ postimage ซ้ำ แล้วคืนเฉพาะ fields ที่ระบบเคยเปลี่ยนด้วย field mask; ห้าม restore ทับการแก้ไขใหม่

## ข้อเสนอการแสดงผลและเวลา

โค้ดต้นแบบ B1 แสดง “พัก” ระหว่างเตรียมซิงก์ และ “ตรวจ” สำหรับสถานะอื่น โดยไม่แสดงว่าแก้ได้ เพราะป้ายอาจค้าง และ C1 แสดงวันที่และเวลาถึงวินาทีในเขต Asia/Bangkok โดยใช้สองบรรทัด เช่น `26/11/03` และ `15:30:44` พร้อม note อธิบายรูปแบบและ “เวลาเกิน 120 วินาทีหรือไม่แน่ใจ ให้งดแก้” ห้ามพึ่งสีอย่างเดียว นี่เป็น mockup เชิงข้อความ ไม่ใช่ผลตรวจว่าพอดีกับขนาดจริง; ต้องทดสอบความอ่านง่ายบน desktop/mobile และ screen reader รวมทั้งการตัดคำ/overflow โดยไม่ทับ D1 หากทำไม่ได้ **อย่าติดตั้งใน B1/C1** ต้องเลือกพื้นที่/วิธีแสดงที่ดีก่อน

รอบซิงก์ประกาศ NOTICE อย่างน้อย 15 วินาที อัปเดต heartbeat และ timestamp ตามรอบที่พิสูจน์แล้ว จากนั้นจึงส่งได้เฉพาะเมื่อ single-writer lock, generation/outer leases, source/identity preimage และการหยุด worker/requests รุ่นเก่าผ่านข้อกำหนด ในกรณี service/browser/offline ค้าง timestamp จะเก่าและผู้ใช้ต้องงดแก้; บราวเซอร์แช่แข็งหรือคนไม่เห็นป้ายยังทำให้เกิดการแก้ชนได้ ไม่ถือเป็น hard lock

หากส่งแล้วไม่ทราบผล, lease หมด, ป้าย/metadata/heartbeat อัปเดตไม่ได้ หรือ postimage ไม่ตรง ให้คง REVIEW ไม่ตั้งแก้ได้และไม่ retry แบบเดา ยอด/ข้อมูลที่อาจถูกเขียนต้อง reconcile ก่อนปลดสถานะ ช่วงซิงก์สำเร็จจึงแสดงสภาวะปกติได้หลังยืนยันผลจริง การเปลี่ยน badge สองช่องควรทำเป็น batch เดียวและตรวจ response/postimage โดยไม่ล้าง fields อื่น

## สิ่งที่ยังไม่เสร็จ

ยังไม่มี heartbeat publisher ที่ตรวจ drain จริง, การลงทะเบียน named ranges ที่พิสูจน์แล้ว, การทดสอบ presentation บนอุปกรณ์จริง, visibility ขณะเลื่อนแนวนอน, rate-control, provider integration หรือ workflow reconciliation ไม่มีการเขียนป้ายหรือสำรองข้อมูลจริงในงานนี้ DAILY dispatch ยังถูกปิด แม้ Google จะ resolve ชื่อช่วงบนเซิร์ฟเวอร์ แต่การอ่าน preimage แล้วเขียนไม่มี CAS; ยังคงมี race กับผู้แก้ที่ไม่ร่วมมือ และต้องเปิดเผยความเสี่ยงนี้ตามจริง

## สถานะต้นแบบตัวเขียนป้าย

มีคลาสตัวเขียนปิดค่าเริ่มต้นและยังไม่มี route ไม่สร้าง named range และไม่มีการเรียก Google จาก public GET. เก็บ preimage ของสองช่องใน D1 แบบจำกัดขนาด ตรวจ identity/ค่า/รูปแบบก่อนและหลัง แล้วคืนเฉพาะค่าที่ระบบเปลี่ยน; unknown หรือข้อมูลไม่ตรงค้าง REVIEW และไม่ส่งซ้ำเอง. ชื่อช่วงต้องติดตั้งล่วงหน้าและตรวจสิทธิ์/สำรองก่อนใช้จริง; ผล mock ไม่ใช่หลักฐานว่า Google ตอบโครงสร้างช่องว่างจริงตามที่ parser คาด. preimage มี userEnteredFormat เต็มซึ่งอาจมีข้อมูลละเอียด ต้องตัดสินใจเรื่องสิทธิ์และ retention ก่อนเปิดใช้งาน.

เมื่อเปิด flag ป้าย การเปลี่ยน AVAILABLE เป็น NOTICE ตรวจว่า journal ป้าย READY ใน SQL เดียว เพื่อไม่เริ่มช่วงใหม่ระหว่างป้าย IN_FLIGHT หรือ REVIEW. ตัวต้นแบบบันทึก receipt ที่ผูก window, source, outer intent และ leases หลังอ่านป้าย NOTICE กลับ แล้วเริ่มนับอย่างน้อย 15 วินาทีจากเวลานั้น; มีต้นแบบ consume receipt ครั้งเดียวพร้อมสร้าง intent ที่ผูก source และ leases ใน D1 statement เดียว และค้าง IN_FLIGHT/REVIEW หากไม่แน่ชัด แต่ยังไม่มี provider writer หรือขั้นตอนตรวจและปลด intent, ยังไม่ตรวจ hidden row/column หรือพิสูจน์การมองเห็นจริง การเขียน DAILY จึงยังถูกบล็อกเสมอ. แม้เพิ่มเติม receipt แล้ว ผู้แก้ที่ไม่เห็นป้ายหรือแก้พร้อมกันยังเขียนชนได้ และ Sheets API ไม่มี CAS. สัญญาณบนชีตที่ค้างไม่สามารถเปลี่ยนเป็น UNKNOWN เองขณะ offline; ต้องดูเวลาและถือว่าสถานะเก่าคืองดแก้.


หลักฐาน receipt และ intent ในต้นแบบห้ามลบหรือ REPLACE และ intent เปลี่ยนได้เฉพาะ IN_FLIGHT → REVIEW; ชื่อ trigger ที่หายจะทำให้ fence หยุด แต่การตรวจชื่อไม่พิสูจน์ว่า SQL ของ trigger ไม่ถูกแก้โดยผู้มีสิทธิ์. หากมี rowid ติดลบ -1 อยู่ SQLite อาจทำให้ INSERT ปกติถูกปฏิเสธแบบอนุรักษ์นิยม ต้องตรวจและแก้สาเหตุ ไม่ข้าม guard. ข้อมูลเก็บรวม source/lease tokens และ preimage จึงต้องกำหนดสิทธิ์ ระยะเก็บ และแผน restore ให้สอดคล้องกันก่อนติดตั้ง.

การกู้คืนเมื่อคำตอบหาย: อ่านสถานะ unresolved จาก D1 โดยไม่แก้ state; หยุดและระบาย writer ทุกทาง จากนั้นตรวจ snapshot ที่สำรองไว้ เทียบ source รุ่นที่ผูกไว้และ identity/ค่าจริงบน Google แยกกรณีตรงก่อนเขียน ตรงหลังเขียน หรือข้อมูลผสม/ไม่แน่ใจ แล้วให้ผู้มีสิทธิ์ทบทวนหลักฐาน. NONE/MISSING ไม่พิสูจน์ว่า Google ไม่เคยรับคำขอ และไม่มี timeout หรือเมธอดปลด/เขียนซ้ำอัตโนมัติในต้นแบบ. ต้องพัฒนาและทดสอบ workflow อนุมัติผลตรวจและกู้คืนจริงก่อนเปิด route.

## ต้นแบบตรวจค้างโดยผู้ดูแล

เส้นทาง `/admin/daily-recovery/*` ปิดเป็นค่าเริ่มต้น และต้องผ่าน bearer `ADMIN_TOKEN` ก่อนอ่านหรือบันทึก; token นี้เป็นสิทธิ์ร่วม จึงระบุได้เพียงว่าใช้ ADMIN_TOKEN ไม่ใช่ตัวบุคคล. การตรวจอ่าน revision จาก D1 ป้ายจาก named ranges และ DAILY row ผ่าน metadata ID กับรหัส X ทั้งชีต โดยไม่ใช้เลขแถวเก่า. หากไม่มีหลักฐาน identity ที่บันทึกไว้ ผลเป็น UNVERIFIED. การพบค่า input ตรงข้อมูลที่บันทึกไว้เป็นเพียงการเปรียบเทียบ ไม่พิสูจน์ provenance ของ identity, สูตรช่วย หรือผลการเขียนใหม่; ตาราง witness ยังไม่มีเส้นทาง enrollment production ที่ผ่านการพิสูจน์.

ผู้ดูแลบันทึก KEEP_REVIEW หรือสั่ง HOLD_IN_FLIGHT ได้ โดยอย่างหลังบันทึก audit กับเปลี่ยน intent เป็น REVIEW ใน SQLite statement เดียว. หาก ACK หาย ให้ inspect สถานะและประวัติ audit ไม่ส่งซ้ำ; การสั่ง HOLD ไม่ยกเลิก HTTP ที่ส่งไปแล้ว. ไม่มีคำสั่งปลด REVIEW, เขียน/ลบ/ซ่อม Sheets หรือสรุปยอดสำเร็จ. ก่อนเพิ่มคำสั่งปลด ต้องมีหลักฐาน preimage/postimage ของคำสั่ง DAILY ที่ผูก source และ identity, ตรวจคน/worker รุ่นเก่าและ request ค้าง, ตรวจ provider ปัจจุบันและ atomic recovery พร้อมขั้นตอนสำรอง/rollback ที่ตรวจแล้ว. Audit เก็บเลขรายการ รหัส intent และ hash ที่ยังอาจอนุมานข้อมูลได้; ADMIN_TOKEN เป็น shared principal จึงต้องกำหนดสิทธิ์และ retention ก่อนเปิดใช้.

## หลักฐานรายการรายวันเดิม — ต้นแบบปิดค่าเริ่มต้น

`DAILY_ROW_EVIDENCE_ENABLED` ยังไม่มี runtime writer: โค้ดเตรียม evidence ได้เฉพาะรายการที่มี identity/baseline witness อยู่แล้วและต้อง derive postimage จาก source ปัจจุบัน ไม่รับยอดหรือรายละเอียดที่ผู้ดูแลพิมพ์มาเอง. ก่อนจองและก่อนเปลี่ยนสถานะ dispatch ตรวจ source/revision/leases, metadata ID กับรหัส X ทั้งชีต, preimage, หมายเหตุ/validation/protection/merge, สูตรช่วย, วันที่ และ subtotal. หากเดือนเป้าหมายจากวันตัดรอบต่างจาก block จริง หรือมีแถวมียอดแต่เดือน/วันผิด ให้ REVIEW; การย้ายข้ามเดือนยังไม่มี workflow ที่รับรองยอดรวมทั้งสองเดือนและห้ามเขียน. ผล ACK จาก D1 ที่หายเป็น OUTCOME_UNKNOWN ไม่ส่งซ้ำ.

Recovery อ่านสูตรและค่าที่คำนวณจาก provider ซ้ำ เทียบ postimage digest และยอดรวมทั้งเดือน แล้วแสดง MATCHES_POSTIMAGE เป็นหลักฐาน ณ ขณะอ่านเท่านั้น. ยังไม่มี provider writer, verified production enrollment, การพิสูจน์การหยุด writer เดิม/HTTP ที่ค้าง, หรือการปิดและปลดเคสแบบ reviewed atomic; แม้ผลตรงยังคง REVIEW. รายการเก่าที่ไม่มี ID รวมถึงรายการใหม่/เพิ่มแถว ไม่ครอบคลุมโดยต้นแบบนี้. การตรวจข้อมูลก่อนเขียนไม่ใช่ CAS และไม่ได้กันเจ้าของหรือ editor ที่แก้พร้อมกัน.

## ผู้สมัครผูก identity รายวันเดิม

เจ้าของอนุมัติให้เตรียม auto enrollment สำหรับคู่ที่ D1/RAW/รายวันตรงกันครบและมี 1:1 โดยไม่ต้องยืนยันทีละคู่. ต้นแบบ preflight ปิดค่าเริ่มต้น อ่าน inventory D1 ของเดือนเป้าหมายและเดือนก่อนหน้า, RAW และรายวันเต็ม grid ตามขอบเขตที่รองรับ แล้วอ่าน RAW/รายวันและ source revision ซ้ำ; ตรวจ RAW ID ไม่ซ้ำและ owned fields ครบ และเทียบเดือนจริง วัน ชื่อ ช่องจ่าย จำนวนเงิน หมวด และแหล่งเงินกับรายวัน. คู่ซ้ำ ผิดเดือน มี ID อยู่แล้ว หรือข้อมูลไม่ครบเป็น HOLD. `PREFLIGHT_ELIGIBLE` ยังเป็นเพียงผู้สมัคร ไม่ผูก ID และไม่รับประกันว่าไม่มีการแก้หลังอ่าน; ก่อน auto enrollment ต้องมี writer lock, การระบาย writer เก่า, ตรวจ metadata ID ทั้ง workbook, durable intent และ audit, อ่าน preimage ซ้ำและจัดการ unknown outcome โดยไม่ retry เดา. ผลสแกนยังไม่ได้รันกับข้อมูลจริงโดยโค้ดนี้.

ต้นแบบยังมี `auditDailyLegacyPreflight` ที่บันทึกหลักฐาน PREFLIGHT_ONLY อัตโนมัติสำหรับคู่ที่ผ่าน โดยเก็บ hash ของ inventory/candidate กับ source revision ไม่เก็บเลขแถว และป้องกันลบ/แก้/บันทึกซ้ำ. เป็นประวัติว่าตรวจพบอะไร ณ เวลาใด ไม่ใช่ใบอนุญาตผูก ID: source/RAW/ชีตอาจเปลี่ยนหลังอ่าน, hash ไม่ใช่การปกปิดข้อมูล และ personal source ยังต้องรวม revision/fence จากงานแยกก่อนใช้งานจริง. ถ้า ACK audit หายต้องอ่านรายการที่บันทึกแล้วก่อน ไม่ส่ง provider mutation ซ้ำ.
