## 2. กติกาและตัวอย่าง

ใช้นาทีสายจริงจากเวลา IN ที่รับรองแล้วเทียบกับ Scheduled_In สำหรับวันและพนักงานที่เปิดใช้นโยบายใหม่ โดยเกณฑ์ V2 เป็น **5 นาทีคงที่** ค่า Grace_Min เดิม เช่น 10 นาที ไม่ขยายเกณฑ์นี้ ส่วนการยกเว้นหักสายของพนักงานยังต้องได้รับการพิจารณาแยกตามข้อ 3

ตัวอย่างพนักงานสมมติสองคน มีคู่ IN/OUT ครบ เปิดหักสายแล้ว และไม่มีรายการหัก/เพิ่มอื่น:

| นาทีสายจริง | ค่าแรงสมมติ 400 บาท: หักสาย | ค่าแรงสมมติ 800 บาท: หักสาย |
|---:|---:|---:|
| 0 | 0 | 0 |
| 5 | 0 | 0 |
| 6 | 50 | 50 |
| 29 | 50 | 50 |
| 30 | 50 | 50 |
| 89 | 50 | 50 |
| 90 | 50 | 50 |
| 300 | 50 | 50 |

50 บาทเป็น **ส่วนหักเพราะมาสาย** ไม่ใช่การรับประกันว่ายอดหักรวมทุกประเภทจะไม่เกิน 50 บาท งานนี้ไม่เปลี่ยน missing punch, early leave, OT, other adjustment หรือเวลาปิดวัน:

- Late กับ missing punch ยังเลือกยอดที่สูงกว่า เช่น ฐานสมมติ 400 บาท สายและขาด OUT: late 50 / missing 200 → ใช้ missing 200 ไม่บวกเป็น 250
- Early deduction ยังแยกต่างหากเมื่อมีคู่เวลาครบ เช่น late 50 และ early 20 → ยอดหักรวม 70 บาท
- อัตราค่าแรงและหลักฐาน IN/OUT เดิมต้องคงไว้ การอนุมัติกติกาสายใหม่ไม่ใช่การอนุมัติเติมเวลา หรือเปลี่ยน wage snapshot

## 3. Interface สำหรับเลือกนโยบายใหม่

| ค่า runtime | รูปแบบและความหมาย | สถานะก่อนอนุมัติเปิดใช้ |
|---|---|---|
| `PAYROLL_LATE_V2_EFFECTIVE_FROM` | วันเริ่มที่ Owner ยืนยัน รูปแบบ `YYYY-MM-DD` เทียบกับ Work_Date | ไม่ตั้งค่า; UNCONFIRMED |
| `PAYROLL_LATE_V2_EMPLOYEE_IDS` | Staff ID ที่ยืนยันแล้ว คั่นด้วย comma ต้องถูกต้องและไม่ซ้ำ | ไม่ตั้งค่า; scope ยังไม่ยืนยัน |

ขาดวันเริ่มหรือไม่มีรายชื่อ จะไม่เลือก V2 สำหรับวันใหม่ ค่าการเปิดใช้สำหรับวันใหม่ที่ไม่ถูกต้องต้องเกิดข้อผิดพลาดชัดเจน ไม่เดาวันหรือขยายเป็นพนักงานทุกคน ตัวอย่าง ID สำหรับ local/test เท่านั้นคือ `TEST_LATE_A` และ `TEST_LATE_B`; ห้ามนำตัวอย่างนี้ไปเปิด Production

Policy code ของ V2 คือ `LATE_V2_GRACE5_FLAT50_CONFIG_OPT_OUT_FIXED_OT_V1` การอยู่ใน activation scope เลือกเวอร์ชันนโยบาย แต่ **ไม่ได้เปิด Deduct_Late แทน Owner** บริบทของวันยังใช้เงื่อนไข `late_deduction_satang > 0`; ค่า 0 ยังคงยกเว้นหักสาย ต้องยืนยันรายชื่อและข้อยกเว้นก่อนปรับค่าที่ใช้งานจริง

ห้ามแก้ `HR_STAFF_CONFIG` H/J/N (`Grace_Min`, `Deduct_Late`, `Late_Deduction_Baht`) เพื่อเปิดกติกาล่วงหน้าก่อนมี engine ที่รองรับ โค้ดฐานเดิมยังเพิ่มยอดเป็น 100 บาทหรือครึ่งค่าแรงเมื่อสายมาก การเปลี่ยนตัวเลขคอนฟิกอย่างเดียวไม่เพียงพอ

### การคงประวัติและบริบทของวัน

- แถวที่มี V2 อยู่แล้วต้องใช้ policy code และข้อมูล snapshot ของวันนั้นต่อ แม้ถอนค่าที่เลือก V2 สำหรับวันใหม่
- V1 ที่มี punch เดิมตรวจโดย replay จาก stored punches, snapshot, OT, adjustment และ finalized state แล้วเทียบผลที่บันทึกไว้ ถ้าตรงกันให้ใช้บริบทของวันต่อ แม้ default schedule หรือคอนฟิกพนักงานปัจจุบันเปลี่ยน; ถ้าข้อมูลไม่ครบหรือผลเดิมขัดกัน ต้องหยุดให้ตรวจ ไม่แทนด้วยคอนฟิกปัจจุบัน
- เมื่อเพิ่มหรือแก้ IN/OUT ของ V1 ต้องตรวจเพิ่มว่า grace, สถานะเปิดหักสาย และจำนวนหักออกก่อนเวลาตรงกับบริบทเดิม มิฉะนั้นหยุดด้วย `V1_CHANGED_PUNCH_CONFIG_AMBIGUOUS` เพราะยอด missing punch เดิมอาจกลบความต่างนี้ได้ ค่าแรงปัจจุบันต่างอย่างเดียวไม่ทำให้ snapshot ที่ replay ตรงถูกปฏิเสธ
- หาก Scheduled_In/Out ปัจจุบันต่างจาก snapshot ต้องตรวจว่าหลักฐานเดิมแยกสองตารางได้หรือไม่ ถ้า late/early minutes เดิมเท่ากันสำหรับด้านที่ตารางต่าง แต่เวลา IN/OUT ที่เติมหรือแก้ใหม่ทำให้จำนวนนาทีต่าง ต้องหยุดด้วย `V1_CHANGED_PUNCH_SCHEDULE_AMBIGUOUS` เช่น เดิมไม่มี IN จึงยังแยกกะ 04:00 กับ 05:00 ไม่ได้ แล้วเติม IN 04:40 ซึ่งให้สาย 40 กับ 0 นาที เงื่อนไขนี้ครอบคลุมด้าน OUT และกรณีเดิมได้ 0 นาทีจากทั้งสองตารางด้วย ใช้จำนวนนาทีตรวจ ไม่ใช้ยอดเงินซึ่ง missing punch หรือขั้นอัตราอาจกลบความต่าง; ตารางกะที่หลักฐานเดิมแยกได้ยังใช้ snapshot ต่อได้
- วันที่บันทึกเป็น V1 แล้วจะยังเป็น V1 แม้ตั้ง effective date ของ V2 ย้อนกลับ การแปลงนโยบายย้อนหลังต้องมีแผนที่จำกัดพนักงาน–วันและผลต่างแยกต่างหาก ไม่เกิดจาก ordinary Payroll Apply
- Legacy code `LATE_V1_FIXED_OT_V1` ที่ไม่ยืนยันบริบท และ policy code ที่ไม่รู้จัก ต้องหยุดให้ตรวจ ไม่ตีความเป็น V2
- การแก้ attendance ย้อนหลังที่มีเวลาแต่ไม่มี daily snapshot ต้องมีหลักฐานบริบทก่อนคำนวณ ไม่ใช้ค่าแรง/สิทธิหักสายปัจจุบันแทนโดยเดา
- Expected shift ที่ไม่มีทั้ง IN/OUT ยังสร้างรายการไม่มีทั้ง IN/OUT รอตรวจได้ตามเดิม แต่ไม่ใช่หลักฐานว่าพนักงานไม่ได้ทำงาน และไม่ได้พิสูจน์สิทธิหักสายของวันนั้นสำหรับการแก้เวลาในภายหลัง

ต้องใช้บริบทเดียวกันใน attendance IN/OUT, admin correction, recalculate, missing-punch finalization และ preview/apply เพื่อให้ preview ตรงกับสิ่งที่จะเขียนจริง

การอนุมัติ OT ขั้นสุดท้ายตรวจบริบทของวันก่อนเขียน OT, audit และ outbox หากบริบทต้อง review จะไม่บันทึกการอนุมัติบางส่วนแล้วค่อยพบว่าคำนวณ payroll ไม่ได้

## 4. Gate ก่อนเปิดใช้จริง

ขั้นตอนต่อไปนี้เป็นแผนสำหรับงาน Production ที่ได้รับอนุมัติแยก ไม่ใช่อำนาจเพิ่มของ Issue #242

1. **ยืนยันคำตัดสินให้ครบ:** Owner ระบุวันเริ่ม รายชื่อและข้อยกเว้น รวมทั้งขอบเขตงวดที่อนุญาตให้คำนวณใหม่อย่างชัดเจน การเลือกวันเริ่มใหม่ไม่อนุมัติย้อนหลังโดยปริยาย
2. **ผ่านการพัฒนาและทดสอบ:** เก็บ exact release SHA, ผล `npm run check`, `npx wrangler deploy --dry-run`, `git diff --check` และ CI ครอบคลุมตารางตัวอย่าง, V1 regression, opt-out, ก่อน/หลัง effective date, scope, คอนฟิกผิด/ไม่ครบ, retained V2, historical-context rejection และ preview/apply parity ใช้ข้อมูลสมมติ ไม่ส่งข้อความหรือสร้าง punch จริงเพื่อทดสอบ
3. **ตรวจฐานจริงและเตรียมกลับคืน:** ต้องอ่าน D1 ได้ ระบุ environment/Worker version/config จริง ตรวจ queue/cron ที่กระทบ payroll และมี private backup ที่ตรวจคืนได้ จัดรายการพนักงาน–วันพร้อมค่าเดิมและ version ก่อนเปลี่ยน การตรวจนี้ต้องรวม backlog ที่ติด review, จำนวน D1 queries/subrequests ต่อ invocation และเพดาน runtime/account จริง โดยวัดกับข้อมูลทดสอบที่มีขนาดและลักษณะใกล้ฐานจริงก่อน Production; cap 300 แถวไม่ใช่หลักฐานว่าพออยู่ใน budget หากยังตรวจไม่ได้ให้ระบุ UNKNOWN หากยัง BLOCKED_D1_SCOPE ให้หยุดเฉพาะการเปิดใช้/แก้ข้อมูล ไม่เปลี่ยนสถานะเป็น APPLIED จาก Sheets
4. **ทำ preview ให้ตรวจได้:** เปรียบเทียบก่อน–หลังด้วยหลักฐานเวลาและ wage snapshot ชุดเดียวกัน โดยใช้บริบท candidate ที่ได้รับอนุมัติใน local/test ก่อน ตรวจผลรายบุคคลและรายสัปดาห์ รวมทั้งคนที่อยู่นอก scope ต้องไม่เปลี่ยน ส่งผลต่างที่มีเหตุผลให้ Owner อนุมัติ release และการเปลี่ยนคอนฟิกจริง
5. **เปิดใช้ตามขอบเขตที่อนุมัติ:** ใช้ exact SHA ที่รองรับทั้งสองเวอร์ชัน ก่อนตั้งค่า activation และสิทธิหักสายตามที่ยืนยัน การเปิดสำหรับวันใหม่ไม่ต้อง recalculation งวดก่อนหน้า อย่าใช้ Payroll Apply เป็นสวิตช์เปิดฟีเจอร์หรือ smoke test
6. **อ่านกลับและกระทบยอด:** ตรวจผล D1 ของวันที่อยู่ในขอบเขต แล้วเทียบ daily/weekly ใน Sheets และงาน sync ตามข้อ 6 จึงบันทึกเวลายืนยันและหลักฐาน APPLIED

คำอนุมัติ Owner ต้องระบุ exact SHA, config, ขอบเขตข้อมูล และการกระทำที่จะทำให้ชัดเจน การอนุมัติครั้งเดียวอาจครอบคลุมหลายการกระทำที่ระบุไว้ได้ แต่ Issue #242 ปัจจุบันยังไม่อนุญาต merge, deploy, เปลี่ยนคอนฟิก Production หรือ Payroll Apply

`POST /admin/payroll/preview` และ `/admin/payroll/apply` เดิมรับทั้งงวด Thursday–Wednesday ไม่ใช่ endpoint แก้เฉพาะพนักงานหนึ่งคน ก่อน apply ต้องตรวจทุกแถวที่จะถูกแตะ รวมถึงแถวนอก activation scope หากคำอนุมัติไม่ครอบคลุมผลข้างเคียงของทั้งงวด ให้หยุดการ apply นี้และออกแบบการแก้ที่มีขอบเขตและ audit แยก

## 6. หลักฐาน read-back และสถานะ Owner

สำหรับแต่ละรายการที่ได้รับผล เก็บ Work_Date, รหัสพนักงานในหลักฐานภายใน, policy code, wage snapshot/source, เวลา IN/OUT, late minutes, late/missing/early deduction, OT, other adjustment, net, confirmed/pending, review/finalized state และ version ก่อน–หลัง ข้อมูลแชร์ใน PR ใช้รหัสสมมติหรือข้อมูลรวม

ตรวจว่า:

- 0/5 นาทีเป็น 0 และ 6/30/90/300 นาทีเป็น 50 สำหรับ V2 ที่เปิดหักสายแล้ว; ผู้ได้รับยกเว้นยังเป็น 0
- preview และค่าที่ D1 เขียนตรงกัน โดยไม่มีการเปลี่ยนเวลา ค่าแรง หรือ policy ของวันนอกขอบเขต
- ยอดรายวันรวมตรงกับรายสัปดาห์; pending ไม่ถูกนับเป็นเงินจ่ายแล้ว; ข้อมูล D1 ตรงกับ Sheet หลัง sync สำเร็จ
- ไม่เกิด duplicate/lost record, audit ขาด หรือ queue/failed-job ผิดปกติจากการเปลี่ยนนี้

งานปิด one-punch ข้ามเฉพาะ `PayrollContextReviewError` และคืน `reviewRequired`/`reviewReasons` โดยไม่ทำเครื่องหมายว่ารายการที่ติด review ปิดแล้ว แต่ละรอบตรวจได้ไม่เกิน 300 รายการ และปิดสำเร็จไม่เกิน 100 รายการ หาก `scanLimitReached=true` ต้องแสดง DEGRADED: ยังมีรายการที่ไม่ได้ตรวจ และหาก 300 รายการต้นลำดับยังติด review รอบถัดไปอาจตรวจกลุ่มเดิมจนรายการถัดไปไม่ได้รับการตรวจต่อเนื่อง จึงยังไม่รับประกันความคืบหน้าของทุกพนักงานจาก cron อัตโนมัติ ต้องตรวจสาเหตุและ budget ตามข้อ 4.3 แล้วใช้ finalizer เดิมที่จำกัดพนักงาน–ช่วงวันตามขอบเขตที่อนุมัติ ค่า `scanLimitReached=false` อย่างเดียวก็ไม่ยืนยันว่าปิดครบทั้งหมด ข้อผิดพลาดชนิดอื่นไม่ถูกกลืนเป็น review

| สถานะที่ Owner เห็น | หลักฐานที่ต้องมี |
|---|---|
| APPROVED RULE / NOT ACTIVATED | อนุมัติเฉพาะกติกา วันเริ่มหรือ scope ยังไม่ครบ หรือ runtime ยังไม่ยืนยัน |
| PENDING | มีงานรอ deploy/config/read-back หรือยังติดสิทธิ์; แสดงเหตุและเวลาตรวจล่าสุด |
| APPLIED | วันเริ่มและ scope ได้รับอนุมัติ, exact deployed version/config ถูกต้อง, ผล D1/daily/weekly ที่เกี่ยวข้องตรวจผ่าน และมี verification reference กับเวลาคงที่ |

เวลาบันทึกคำตัดสินและเวลายืนยันใช้จริงเป็นคนละช่อง ห้ามใช้ `NOW()` หรือการแก้คอนฟิกใน Sheets เป็นหลักฐานแทนการอ่านฐานจริง

## 7. Rollback ที่รักษานโยบายของวันเก่า

ก่อนเปิดใช้ให้บันทึก config เดิมและ Worker version ที่รองรับประวัติทั้ง V1/V2 หลังมีแถว V2 แล้ว **ห้ามย้อนกลับ Worker รุ่นที่อ่าน V2 ไม่เป็น** เพราะการรับ OUT, correction, cron หรือ recalculate อาจนำกติกาเก่าไปคิดกับวัน V2

หากมีปัญหา ให้หยุดงานเปิดใช้/คำนวณเพิ่มเติมที่ยังไม่ดำเนินการและรักษาหลักฐานก่อน ใช้แผนที่ Owner อนุมัติเพื่อถอนการเลือก V2 สำหรับวันใหม่โดยคงการอ่าน V2 เดิม หรือ deploy forward fix/เวอร์ชันที่รองรับทั้งสองนโยบาย การถอน activation ไม่ใช่คำสั่งแปลงประวัติ V2 กลับเป็น V1

ตรวจรายการที่เขียนจริงและแบ่งจ่ายแล้ว/ยังไม่จ่ายอีกครั้งก่อนแก้ยอด ใช้ audit และผลต่างเฉพาะรายการ ไม่ลบ policy code, attendance evidence หรือ payroll run แล้วเริ่มใหม่ การย้อน Worker อย่างเดียวไม่ย้อนข้อมูล D1 ที่เขียนไปแล้ว
