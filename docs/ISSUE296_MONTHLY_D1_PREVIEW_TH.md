# รายงานค่าใช้จ่ายจาก D1 สำหรับ #296

สถานะ: โค้ดต้นแบบอยู่ระหว่างทดสอบ ยังไม่ได้ deploy, migrate หรือเขียน Production. ฐานงาน canonical main `b930101b6dfbca5ed4e6721728a238d7415b5ecc`; งานบนข้อมูลจริงมีความเสี่ยงสูง ต้องผ่าน review, CI, backup/restore, ซ้อมและตรวจ Production gate ก่อน

การตั้ง `MONTHLY_REPORT_OPERATOR_ENABLED=true` ใน config เป็นการเตรียมเปิด route สำหรับงาน #296 ตามคำสั่งเจ้าของ; ค่าใน repository ไม่ใช่หลักฐานว่า deploy หรือส่งรายการจริงแล้ว.

เลือก expense_events ที่ `CONFIRMED` และ transaction_date อยู่ในเดือนปัจจุบันตาม Asia/Bangkok ตรวจข้อมูลและ mapping กับ header ในชีต พักรายการที่ข้อมูลไม่ครบหรือกำกวม แล้วเขียนครั้งละหนึ่งรายการในแท็บ `รายวันต่อเนื่อง_แบบร่าง` เจ้าของยอมรับรายการและยอดแสดงผลที่อาจซ้ำกับของเดิม ห้ามสร้างหรือแก้ธุรกิจใน D1, ทับสูตรหรือข้อมูลที่มี, ส่งคำสั่งที่ผลไม่แน่ชัดซ้ำ หรือแก้คิวอื่นนอกขอบเขต

Workflow มี PREVIEW และ INSPECT สำหรับอ่าน และ APPEND_ONE ซึ่งอ่าน PREVIEW สดภายใน run เดียวกัน ก่อนส่ง projection สูงสุดหนึ่งครั้ง จากนั้นตรวจ row และบันทึก receipt แยก รายการที่ receipt ยืนยันแล้วใน run เดียวกันจะไม่ถูกเลือกซ้ำในการรอบถัดไป ส่วนการพบรายการในชีตเดิมเพียงอย่างเดียวไม่ตัดออก การประมวลผลหลายรายการต้องเรียก workflow แยกทีละรอบ ยังไม่มี scheduler อัตโนมัติและยังไม่มีขั้นตอนเปลี่ยนเดือน

หากผล D1 หรือ Google ไม่ชัดเจน ให้ใช้ INSPECT อ่านหลักฐานโดยไม่ส่งซ้ำ ระบบคง intent และหยุดการเขียนใหม่ในช่วงที่ยังพิสูจน์ request เก่าไม่ได้ เพราะแถวเป้าหมายอาจชนกัน; อย่านำรายการค้างไปเขียนใหม่เพื่อข้าม guard แม้รายการ source ไม่ครบก่อน dispatch สามารถพักและเลือกข้อมูลพร้อมถัดไปได้

ต้องมีผู้เขียนภายนอกและการแก้ไขด้วยมือถูกพักตลอดการตรวจและเขียน พร้อมผู้รับผิดชอบเฝ้าดู; ตรวจ claim, worker version, ข้อมูลต้นทาง, ชีตและหลักฐาน original incident สดอีกครั้ง ไม่ถือว่า preview เป็นสิทธิ์เขียนด้วยตัวเอง. Backup สำหรับ report ต้องเป็น private backup ที่ซ้อม restore, checksum และ integrity ผ่าน ตรง SHA ที่จะใช้ และเกิดหลัง incident เวลา `2026-11-21T10:07:19.486Z`; ให้สร้าง fresh backup ก่อน pilot. Migration มี gate backup ไม่เกินหนึ่งชั่วโมงตาม runbook แยกต่างหาก

การเพิ่ม DAILY ไม่ได้ทำให้ RAW, DETAIL หรือรายงานทุกชุดซิงก์ครบ การทดลองบนสำเนาพบรายงาน 35 เปลี่ยน แต่ช่วงที่ตรวจในรายงาน 34 และ 97 ไม่เปลี่ยน จึงห้ามอ้างว่าระบบหรือยอดรายงานทั้งหมดเสร็จ. Claim และ incident เดิมยังคงอยู่; overlay verification รักษาหลักฐานเพื่อพัฒนาการกู้ต่อ แต่ไม่ได้ปลดล็อกหรือยืนยันว่าการกู้เดิมเสร็จ. Owner edit หรือ Undo ระหว่างการทำงานต้องหยุดตรวจและไม่ลบข้อมูลอัตโนมัติ

PREVIEW แสดงจำนวนพักแยกตามเหตุผลใน workflow logs; authenticated admin response แสดงรหัสรายการที่รูปแบบตรวจผ่านพร้อมเหตุผลโดยไม่แสดงรายละเอียดธุรกรรม ส่วนวันที่ผิดรูปจนระบุเดือนไม่ได้แสดงเป็นจำนวนแยกโดยไม่เดาว่าอยู่ในเดือนนี้. `stale` คือจำนวน receipt ที่ source เปลี่ยน/ยกเลิก/หาย ไม่ใช่จำนวนรายการซ้ำกับชีตเดิม และยังไม่ทราบจำนวนซ้ำทั้งหมด. ขณะนี้รับต้นทางได้สูงสุด 500 รายการต่องวด หากมากกว่านั้นจะพักเพื่อแก้ขอบเขตก่อน ไม่อ้างว่าครบทั้งเดือน

เมื่อ PREVIEW ตอบ HELD ให้แสดงเฉพาะชื่อขั้นตรวจและประเภทข้อขัดข้องจากรายการที่กำหนดไว้ (รวมคำขอย่อยของ grid, HTTP status และชื่อ field จาก allowlist เมื่อตรวจได้) โดยไม่แสดง provider body, ข้อมูลต้นทางหรือ credentials; คำขอที่ทำพร้อมกันอาจล้มมากกว่าหนึ่งรายการแม้แสดงเพียงรายการที่ตอบล้มก่อน. ระบบยังหยุดก่อนเขียน และผลวินิจฉัยไม่ใช่สิทธิ์ปล่อย claim หรือส่งซ้ำ. INSPECT และ APPEND_ONE คงเงื่อนไขเดิม รวมถึงข้อกำหนดตรวจหลักฐานก่อนเขียน. การมี code เปลี่ยนใน repository ไม่ใช่หลักฐานว่า deploy หรือแก้ Production แล้ว.

การข้ามรายการที่ติดล็อก (#296) มีผลเฉพาะรายงานรายเดือน ความเสี่ยงสูงเพราะใช้ตัวส่งแถวจริง เกณฑ์รับงานคือรายการของ incident ที่ตรงทั้ง ID และรุ่นต้องถูกพักด้วยเหตุ INCIDENT_REVIEW รายการอื่นที่พร้อมยังถูกเลือกได้ตามลำดับ หลักฐานคิวและธุรกรรมต้นทางต้องคงเดิม การทดสอบ Miniflare บนฐาน 2e1811e พบว่าตัวเลือกเดิมกรองเฉพาะรายการที่มี receipt จึงเลือก incident ได้ การเปลี่ยนเกณฑ์นี้ไม่แก้ข้อผิดพลาด GRID_FULL_INITIAL ของ Google ต้องตรวจ PREVIEW และผลเขียนจริงก่อนยืนยันการส่ง หากต้องย้อนรุ่นให้หยุด APPEND_ONE เพื่อป้องกันการเลือกรายการที่พัก
