## Invariants ที่เสนอ

1. ชุดสมาชิกของรอบและเดือน/รุ่นที่จองตรึงใน D1 แบบ immutable; job หนึ่งปรากฏได้ครั้งเดียวต่อรอบ. รอบกู้ต้องอ้างรอบเดิม และไม่มีการตีความ snapshot เดิมใหม่เมื่อปิดแล้ว.
2. ผลสมาชิกมีเพียง verified, safely parked, reconciliation required หรือ not started; ผลรอบปิดซ้ำได้ผลเดิมและยอดรวมเท่าจำนวนสมาชิก รวมชุดว่าง. หากปิดไม่ได้ให้คงรอบเปิดเพื่อให้ตัวตรวจตามปิดหลังบริการฟื้น โดยไม่อนุมานว่า runner ที่หายหยุด provider แล้ว.
3. สายจองมี successor ไม่เกินหนึ่งต่อ predecessor; proof, การ fence สิทธิ์เดิม, การปิด epoch เดิมและการเปิด epoch ใหม่ต้องตรวจและ commit ในธุรกรรม D1 เดียว. ไม่ลบหลักฐาน A หรือ B.
4. ผล provider ไม่ชัดรวมทั้ง timeout, response loss, lease หมด และการอ่านไม่พบครั้งเดียว ต้องคง claim และ journal; การอ่านย้อนหลังไม่เปิดสิทธิ์เขียน. Cross-version แบบอ่านอย่างเดียวต้องตรวจชนิดและรุ่นหลักฐานที่รองรับ มิฉะนั้นแจ้งเหตุและวิธีกระทบยอด ไม่อนุมานว่าสำเร็จ.
5. Progress มาจากขั้นที่ VERIFIED ล่าสุดและเวลา รวม DETAIL แต่ละรายการ; แยก inactivity timeout จาก absolute cap และบันทึกตำแหน่งรับช่วงเมื่อครบ cap.

## จุดที่ต้องพิสูจน์ก่อนเปิด safe park

แนวทางแคบที่เสนอเริ่มจาก B ยัง `PENDING`, attempt_count=0, ไม่มี lease, epoch `ARMED`, claim `PILOT_RESERVED`, และไม่มี operation, projection หรือ notice intent/dispatch ของ B. แม้ตรงทั้งหมด ยังต้องพิสูจน์ว่า request ที่สืบทอดจาก A โดยเฉพาะ notice ไม่มีทางค้างหรือส่งผลภายหลัง และต้องกัน cron/Worker ที่กำลังรับ B แข่งกับการพักผ่าน CAS เดียวกัน. `beginNoticeMayHaveWritten` ใน `stable-workbook-claim.ts` แสดงว่า absence ของ projection เพียงอย่างเดียวไม่พอ. ยังไม่มี proof ที่ผ่านการทบทวน จึง **ห้ามเปิด safe park จากเงื่อนไขข้างต้นเพียงลำพัง**.

`stable_recovery_one_active_epoch` ไม่ยอมให้ REVIEW และ ARMED ซ้อน; การเปลี่ยน REVIEW → CLOSED เพียงอย่างเดียวไม่พิสูจน์ provider เงียบ. Operation ADMITTED เปลี่ยนเป็น VERIFIED ได้ภายใต้หลักฐานจริงเท่านั้น ห้ามเปลี่ยนสถานะเพื่อทำให้เปิด C ผ่าน. การตัดสิทธิ์ writer และการตรวจ request ครบทุกชนิดต้องเป็นส่วนหนึ่งของ proof ที่ guard ในธุรกรรมจอง.

## การทดสอบที่ต้องมี

ใช้ D1 จำลองจริงในเครื่องและ provider จำลองฉีด fault: B/C จองแล้วคำตอบหาย, Google รับแล้วตอบหาย, runner ถูกตัดทั้งก่อนและหลังจอง, แข่งพัก/รับ lease/จอง C, evidence เปลี่ยนระหว่างอ่านและ commit, ปิดรอบซ้ำ, D1 ขัดข้องแล้วกลับมา, เดือนเปลี่ยน, รุ่นเปลี่ยน, ไม่มี/ขัดกับ snapshot, ชุดว่าง และหลาย DETAIL พร้อมทั้งยืนยัน claim ที่กำกวมไม่ถูกปล่อยและไม่มี request เขียนซ้ำ. ผ่านชุดเดิมและ `npm run check` กับ `npx wrangler deploy --dry-run`; ต้องทบทวน flow และ published views เทียบ implementation ก่อนปิด Issue.

## ผลตรวจร่าง storage และขอบเขตที่ยังไม่ผ่าน

มี migration และ helper ทดลองใน branch นี้สำหรับ snapshot สมาชิก ปิดผลอย่างอะตอมมิก และค้นรอบ OPEN โดยผลที่ caller ส่งเป็นข้อมูล bookkeeping ที่ยังไม่ใช่ proof ห้ามนำไปให้สิทธิ์หรือรายงานว่ารายการยืนยันแล้วก่อนมี classifier ตรวจหลักฐาน D1/provider และตรวจซ้ำภายในธุรกรรม การปิดและอ่านกลับเมื่อคำตอบหายผ่าน SQLite ในเครื่อง; การแข่ง audit/close และ rollback ผ่าน local D1 สังเคราะห์ แต่ยังไม่ใช่ race ของ Worker และ provider จริง เชื่อม endpoint สำหรับตรวจรอบ; `DISCOVER_ROUND` ค้นย้อนหลังและ `RECOVER_ROUND` อ่านรอบเดิมเท่านั้น หากยัง OPEN ให้หยุดกระทบยอดโดยไม่สั่งปิดซ้ำ และ `RUN_SERIAL` โหมดทดลองสร้าง/ใช้ snapshot และระบุ roundId แต่ยังไม่พร้อม merge/migrate. เพดานทดลอง 100 สมาชิกเป็นขีดจำกัดท้องถิ่น ไม่รับรอง latency ของ D1; [เอกสาร Cloudflare](https://developers.cloudflare.com/d1/platform/limits/) ระบุทั้ง batch อยู่ในกรอบเวลา 30 วินาที.

การตรวจอิสระพบว่า `attempt_count=0` ไม่พิสูจน์ว่า B ไม่เคยรับ lease: `stable-phase1-dispatch.ts` อาจคืนค่านี้เมื่อ defer ขณะที่ `sync.ts` ล้าง error เมื่อ claim. การบันทึก lease ตั้งแต่หลังจองก็ไม่ครอบคลุมประวัติก่อนจอง จึงต้องมีหลักฐาน provenance ตั้งแต่ก่อนเริ่มงาน หรือปฏิเสธกรณีไม่อาจพิสูจน์. สำหรับ request เดิมของ A ยังไม่มีหลักฐานคงทนที่พิสูจน์ว่า notice/provider request ทุกชนิดสิ้นสุดแล้ว; ต้องระบุและพิสูจน์ fence ของ old worker และ provider ก่อนนำ safe park ไปใช้งาน.

ยังขาด D1 evidence classifier และ CAS ที่เชื่อม readback กับผลรอบ, pagination ค้นรอบที่ยังเปิดและผลที่ปิดแล้ว, recovery หลัง process หายโดยไม่อาศัยค่าใน memory, provenance ของ snapshot เดือน/รุ่นและการกู้ทั้งรอบข้ามรุ่น, การพิสูจน์ progress หลาย DETAIL ด้วย Worker/D1 จริง, safe park และการทดสอบตาม acceptance. ร่างนี้เพิ่มเส้นทางค้น/ปิดแบบรอกระทบยอด แต่ยังไม่ได้อัปเดต diagram หรือ published views; ต้องอัปเดตและตรวจเทียบ implementation ก่อนเสนอส่งมอบหรือปิดงาน.

ตัวอ่าน `READ_HISTORICAL` เป็น read-only และต้องมี snapshot พร้อม audit/epoch/admission/date ตรงกัน; Miniflare synthetic ทดสอบเดือนและรุ่นเปลี่ยนแยกกัน แต่ snapshot ที่ fixture สร้างเองไม่พิสูจน์ provenance จริง. `FINISH_PROGRESS` ใช้ชุด hash ของขั้นที่ตรวจแล้วและ source revision แบบ global; การเปลี่ยน revision จากรายการอื่นอาจทำให้หยุดแบบ fail closed. ผล VERIFIED receipt ทดลองใช้ปิดรอบภายใต้สมมติฐานที่ระบุด้านล่าง แต่ยังไม่ผ่านการพิสูจน์ trust boundary และ fence สำหรับใช้งานจริง. `serial_pilot_fence_not_ready` ป้องกัน activation ของร่างนี้; synthetic tests ถอดเฉพาะในฐานจำลองเพื่อทดสอบ.

## ความคืบหน้าร่าง classifier และข้อจำกัด

ทดลอง `RECORD_VERIFIED` และ `CLOSE_VERIFIED` โดยยืนยัน status, provider readback และ status อีกครั้งก่อนเก็บ receipt; ตอนปิดตรวจ completion, revision, audit chain, successor และไม่มี claim ใดใน workbook ใน D1 batch เดียว. การอ่านผลปิดซ้ำตรวจ receipt และ audit chain ที่ตรงกัน ผลนี้เป็นหลักฐาน ณ เวลาอ่าน ไม่ใช่สิทธิ์ให้ ADVANCE และยังต้องอ่านซ้ำก่อนจอง successor. ร่างนี้สมมติว่าผู้เขียน D1 ทั้งหมดเชื่อถือได้และ external writer fence คงอยู่ตั้งแต่ readback ถึงปิด/จอง; trigger หรือ SHA ไม่พิสูจน์ผู้สร้าง receipt หรือกันการเปลี่ยนชีตภายนอก. การทดสอบ Miniflare ใช้ Google จำลองและยก barrier เฉพาะฐานทดสอบ จึงไม่พิสูจน์สมมตินี้ในระบบจริง.

ชุด local ทดสอบ receipt/close ตอบหาย, หนึ่งและสองรายการ, claim ของ writer อื่นและ source เปลี่ยนหลัง receipt; รอบยัง OPEN หาก CAS ไม่ผ่าน. เพดาน 100 รายการยังไม่มีผลทดสอบเวลาของ batch ขนาดสูงสุด (ประมาณ 302 statements และ CTE ซ้ำ) จึงไม่รับรองว่าอยู่ในเวลา D1. ผล RECONCILE ยังไม่ใช่การจำแนกสี่หมวดตาม acceptance; safe park, หลักฐาน provider quiescence, provenance เดือน/รุ่น และการกู้ข้ามรุ่นยังไม่ครบ. ห้ามเปิด activation barrier หรือเสนอ migration นี้เป็นงานพร้อม merge/release จนพิสูจน์และตรวจครบ รวม flow และ published views.

`READ_ROUND` ในร่าง runner อ่านผล CLOSED/ALL_VERIFIED จาก Worker รุ่นปัจจุบันได้แม้ receipt มาจากรุ่นเดิม โดยแสดงรุ่นและเวลาที่บันทึก การอ่านไม่ตรวจ integrity ของ chain ซ้ำ ไม่ตรวจสถานะ provider ปัจจุบัน และไม่ให้สิทธิ์จองต่อ; Miniflare และ runner fixture ตรวจว่าไม่มีการจอง ส่ง queue หรือเขียน provider. `CLOSE_VERIFIED` retry ข้ามรุ่นยังหยุดแบบ HELD และยังไม่ถือว่าการกู้ทุกกรณีข้ามรุ่นผ่าน.

Observation เพิ่มจำนวน operation `ADMITTED` ของ epoch ที่ผูกกับงานและความสัมพันธ์ claim ของ workbook กับ operation ใน epoch นั้น โดยไม่แสดง token. `UNKNOWN` ต้องตรวจเพิ่ม และ `NO_CLAIM` แปลเพียงว่าไม่พบ claim ณ เวลาที่อ่าน ไม่พิสูจน์ว่า provider request สิ้นสุด; observation ไม่ atomic กับ snapshot รอบ ไม่ใช่ classifier หรือสิทธิ์ส่งต่อ.

Recovery แสดง provenance version/generation เพื่อช่วยตรวจเท่านั้น: version 0 เป็น UNKNOWN, generation 0 ไม่พิสูจน์ no lease และไม่มีค่าใดให้สิทธิ์ C โดยลำพัง. Route ตรวจคอลัมน์ที่ต้องมีจาก 0069 ก่อนปิดรอบ หากขาด/ไม่ครบตอบ `PROVENANCE_SCHEMA_UNAVAILABLE` และคงรอบเปิด; การอ่านนี้ยังไม่ตรวจ integrity ของ marker/trigger.

Migration ทดลอง 0069 ใช้ provenance version และ lease generation บนแถว `sync_jobs` เฉพาะ EXPENSE โดยค่า 0 สำหรับงาน legacy หมายถึง UNKNOWN; marker ผูก workbook และ version 1 ต้องมี post-cutover membership และ source version 1 ตรง ณ INSERT. Barrier แยกยังปิดอยู่. โหมดทดลองเชื่อม confirm, outbox/claim และ batch enqueue หลัก; D1 fixture ตรวจ generation ใน statement เดียว, confirm/claim แข่ง, old Worker และ rollback. Mixed batch และ force redrive ถูกปฏิเสธก่อนส่ง, ส่วน undo version 2 ยังเป็น version 0; เมื่อเปิด flag wrapper ยังตรวจ readiness กับ expense นอก cohort และ legacy duplicate ใน cohort อาจถูก fence จึงยังไม่ผ่าน parity. Schema/trigger integrity และ flag drift ยังต้องพิสูจน์; counter ไม่พิสูจน์ provider quiescence ของ A และยังไม่มี consumer ใช้อนุญาตพักหรือส่งสิทธิ์. ห้ามเปิด barrier.

แนวทาง side-table ก่อนหน้านี้ทำให้ D1 `meta.changes` นับแถว trigger เพิ่มจน outbox และ claim ที่คาดค่า 1 ทำงานผิด; เปลี่ยนร่างมาใช้ counter ในแถวเพื่อลดผลดังกล่าว แต่ยังต้องตรวจทุก producer/claim/redrive และ test rollout ก่อนใช้จริง.

Migration ทดลอง 0070 เพิ่ม source namespace แบบ opt-in หลัง marker สำหรับ text draft เท่านั้น และห้าม backfill/ลบ/แทนที่ source ที่ระบุ namespace. Job version 1 ต้องผูก source namespace/book กับ marker และ guard 0070; source เดิม, quick-save และ image paths เป็น UNKNOWN. Namespace ใหม่ช่วยจำกัดการเกิด identity ใหม่ภายใต้สมมติฐาน writer ที่ถูกควบคุม แต่ข้อมูลปัจจุบันไม่พิสูจน์ว่า old writer หรือ provider request หยุดแล้ว. Migration 0071 และ action `HOLD_RESERVED` ทดลอง CAS บันทึกหลักฐานและเปลี่ยน B เป็น REVIEW โดยคง claim HELD/PILOT_RESERVED และ epoch ARMED; ผล `RECONCILIATION_REQUIRED` ไม่ใช่ safe park และไม่ส่งสิทธิ์ C. Barrier ของทั้งสาม migration ยังคงปิด; ต้องทดสอบและทบทวน end-to-end/rollback/forward-fix ก่อนเสนอใช้.

Runner ทดลอง `HOLD_RESERVED` ตรวจ backup/owner/fence แล้วอ่าน root ของรอบก่อนส่งคำขอครั้งเดียว; ถ้าคำตอบหายให้ดู round/job และหลักฐานเดิม ไม่ส่งซ้ำอัตโนมัติ. Miniflare ใช้ marker/Google จำลองทดสอบ hold ชนะ/lease ชนะ/แข่ง, batch rollback, ACK หายและ stale queue โดยไม่สร้าง C; ไม่ใช่หลักฐาน provider quiescence หรือ Production.

ตัวตรวจ Ed25519 ทดลองตรวจลายเซ็นของคำรับรองที่ผูก context และเวลาจำกัด ไม่มี key จริง, endpoint, nonce consumption หรือการจอง C. ลายเซ็นยืนยันผู้ลงนามเท่านั้น ไม่พิสูจน์ว่า provider หมด request ค้างหรือ external fence ยังอยู่; #296 ต้องกำหนดผู้รับรองที่เชื่อถือได้และหลักฐาน/กลไกคง fence ก่อนมี authority. D1 ต้องตรวจข้อมูลและใช้ nonce แบบอะตอมมิก รวมทั้ง C adoption ต้องรองรับ hold lineage ก่อนส่งสิทธิ์ได้.

การทดสอบ D1 พบว่า confirm เดิมตรวจ `meta.changes` ของ source ที่มี trigger อื่นและอาจคืน null แม้ commit สำเร็จ จึงเปลี่ยนเป็น `UPDATE ... RETURNING` ตรวจ identity/version ของแถวตรงและตรวจ scope รอบ batch; คำตอบหรือ scope หลัง commit ที่ไม่ชัดรายงาน UNCERTAIN ไม่ replay.

ร่าง 0072 ทดลอง oracle จำลองโดยมี barrier แยกที่ยังปิดจริง: D1 CAS ผูกลายเซ็นกับ context และ nonce พร้อมบันทึก edge โดยไม่ปล่อย claim ระหว่าง B และ C. Miniflare ทดสอบ rollback กลาง batch, ACK หายหลัง commit, fence เปลี่ยน, ลายเซ็นผิด และ expiry หลัง DAILY POST (claim คง REVIEW และไม่ส่งซ้ำ); ผล `RESERVATION_RECORDED` เป็นบันทึกย้อนหลัง ไม่ใช่สิทธิ์เขียนปัจจุบัน. C รับ edge จำลองผ่าน Worker และเขียน DAILY จำลองได้หนึ่งครั้ง แต่หลัง notice-ready จะคง claim เป็น REVIEW ด้วย `ATTESTED_PILOT_RELEASE_UNVERIFIED`; job อาจยัง PENDING และ queue เก่าต้องไม่เขียนซ้ำ. ยังขาด release receipt ที่ผูก notice postimage และ transaction ปล่อย claim กับ fence/expiry/evidence รวมทั้งกรณี ACK หายหลังปล่อย ตลอดจนการทดสอบ RAW/DETAIL/FINAL และ expiry ระหว่าง provider request. ลายเซ็น/fence จำลองไม่พิสูจน์ quiescence หรือ external fence จริง; ห้ามเปิด barrier จน gate #296 และเกณฑ์ทั้งหมดผ่าน.

ร่าง 0073 เพิ่ม immutable notice-release receipt โดย barrier ปิดอยู่ และ helper ทดลองแบบไม่มี caller: ภายใน batch ตรวจหลักฐาน DAILY/edge/fence/expiry, เปลี่ยน operation เป็น VERIFIED, บันทึก receipt และลบ claim พร้อม guard rollback. Miniflare fixture ใช้ digest จำลองตรวจ barrier, observation เก่า/อนาคต, rollback, ACK หาย, การเรียกพร้อมกัน และ replay เมื่อ writer ใหม่ถือ claim; `RELEASE_RECORDED` บอกเพียงผลย้อนหลังของ token เดิม ไม่ยืนยันว่า workbook ว่าง. ก่อนเชื่อมต้องรับ digest/time จาก readback ของ Worker โดยตรง และบังคับ authoritative fence ตลอด RAW/DETAIL/FINAL ทุกครั้งที่รับ claim, ก่อน/หลัง provider และก่อน release; C หลาย DETAIL ยังไม่ผ่าน. 0073 ไม่พร้อม merge/migrate/release.

ร่าง 0074 ทดลอง session fence และ permit ผูก C/epoch/lease generation โดยเริ่ม session ใน batch release แรก; trigger กัน claim ของงานอื่น, REPLACE/UPDATE ข้าม book และกันลบ claim เมื่อ revoke/หลักฐานไม่ครบ. SQLite และ Miniflare ใช้ fixture สังเคราะห์ตรวจ permit+claim rollback, lease/epoch drift และ ACK หาย; helper ยังไม่มี Worker caller, release ของ RAW/DETAIL/FINAL และ completion ถูก block โดยตั้งใจ. Revocation เป็นเพียง stop signal ใน D1 ไม่พิสูจน์ว่า request เดิมจบแล้ว; coordinator ภายนอกต้องคง fence จนกระทบยอด. ทุก activation barrier ยังคงปิดจริงและ 0074 ไม่พร้อม merge/migrate.

ร่าง 0075 ทดลอง receipt และ release แยกแต่ละ RAW/DETAIL: helper อ่านหลักฐาน ledger/journal/marker/preimage/source และ notice observation แล้วบันทึก receipt ขณะคง claim; release helper ตรวจซ้ำและ VERIFY operation + DELETE claim ใน batch. Permit ถัดไปตรวจ journal↔receipt ทั้งสองทาง. Miniflare ใช้ carrier writer จริงกับ provider/notice digest จำลอง ทดสอบ RAW และ DETAIL สองรายการ, ลำดับผิด, receipt เกิน, source/marker/trigger เปลี่ยน, revoke, rollback, ACK หายและ release แข่ง; เป็นการเรียก helper ตรง ไม่ใช่ Worker E2E. Completion guard ยังคง block FINAL เสมอ, helper ยังไม่มี runtime caller, external writer fence และ provider quiescence ยังต้อง #296. 0074 สร้างตารางและ barrier ของ 0075 ใน transaction เดียวกันเพื่อกัน partial migration; ทั้งหมดเป็นร่างห้ามเปิด barrier.

Trigger ในร่าง 0074 ตรวจชุดชื่อ guard/barrier ภายใน session/permit/claim acquisition และ DELETE ด้วย; SQLite ถอด guard ทีละตัว (ยกเว้น trigger ที่กำลังป้องกันเอง) แล้ว direct acquire/delete ต้องล้ม. นี่พิสูจน์เฉพาะ trigger หาย ไม่พิสูจน์ body ถูกแทน และยังต้อง trusted DDL. RAW/DETAIL local helper ได้ทดสอบ release แบบ D1 batch โดยไม่ปลด claim guard ระหว่าง stage แล้ว แต่ notice digest/provider ยังสังเคราะห์ และ FINAL/completion กับ Worker integration ยังไม่พร้อม.

ความคืบหน้า Worker mock ภายใต้ `APP_ENV=test` และ flag เฉพาะ: เคยทดสอบ DAILY → RAW → DETAIL สองรายการด้วย provider จำลอง โดย FINAL ยังคง REVIEW และ completion barrier ปิด; ยังไม่ใช่เส้นทาง C สำเร็จ. หลังทดสอบนั้นเพิ่ม phase ถาวรให้ claim ของ C และ continuation เพื่อไม่ให้กลับไป legacy เมื่อ binding ในหน่วยความจำหายหรือ flag เปลี่ยน พร้อม guard กัน DELETE/REPLACE/identity/phase ก่อนสร้าง session; SQLite schema test ผ่าน 5/5 ส่วน Worker/D1 ของ revision ใหม่นี้ยังรอผล. การเปิด normal notice handoff ร่วม mock ถูกปฏิเสธก่อน dispatch. ยังต้องทดสอบ fault ระหว่าง network, runner restart และ final receipt/atomic completion รวมถึง old Worker และ external fence ตาม #296; ไม่มีหลักฐานว่าคำขอ provider เก่าหยุดจาก mock นี้.

FINAL mock เริ่มจับ projection snapshot ใน invocation เดิม แต่ยังไม่ใช้เป็นสิทธิ์ปิดงาน: เมื่อผลรายการเป็น COMPLETED จะหยุดก่อนส่ง notice READY และคง claim เพื่อ REVIEW พร้อมเหตุ `SERIAL_FINAL_COMPLETION_NOT_READY`. ยังไม่สร้าง final receipt หรือ completion และยังต้องทดสอบ D1/Worker revision นี้ รวมทั้งพิสูจน์ลำดับ recovery, notice และ external fence ก่อนปล่อยใช้งานจริง.

ขั้นที่ยังต้องพัฒนาสำหรับ FINAL ภายใต้ oracle จำลอง: ผูก snapshot ของ verifier กับ claim, lease, epoch และ source; ตรวจ external fence ก่อนและหลัง notice; บันทึก postimage จาก readback ภายใน Worker; แล้วให้ D1 transaction ตรวจ receipt, exact stage set, source revision, failure/operation, fence และ claim อีกครั้งก่อนเปลี่ยน operation/epoch, บันทึก completion และปล่อย claim. หาก READY หรือผล D1 ไม่ชัดต้องคง claim หรือหลักฐาน durable เพื่อ reconcile โดยไม่ส่งซ้ำ. READY กับ D1 ไม่ atomic กัน จึงยังต้องมี external fence ที่บล็อกผู้เขียนและผู้ใช้ต่อเนื่องแม้ runner ตาย ซึ่ง mock D1 ไม่พิสูจน์; #296 ต้องยืนยันเงื่อนไขนี้แยกต่างหาก. ชุดทดสอบต้องครอบคลุม 0 และหลาย DETAIL, source/fence/lease เปลี่ยน, ACK หายและตัดตัวรันก่อน/หลังแต่ละ commit, กับการแข่ง claim/complete.
การออกแบบ batch จบต้องคำนึงถึงลำดับ trigger ปัจจุบันด้วย: claim serial ถูกห้ามลบเมื่อไม่มี active session ดังนั้นห้ามบันทึก completion ก่อน DELETE โดยไม่ออกแบบ guard ใหม่และพิสูจน์ atomic rollback; การอ่าน receipt เดิมหรือการไม่มี claim เพียงอย่างเดียวไม่ให้สิทธิ์ส่งงานต่อ.

การอ่านรอบเพื่อรับช่วงแสดงสถานะ, phase และเหตุของ claim ทั้งไฟล์เฉพาะค่าที่อนุญาต; ค่าอื่นเป็น UNKNOWN และไม่มี claim เป็น null. ค่านี้อาจเป็น claim ของงานอื่น ไม่ใช่หลักฐานสิทธิ์ของรายการ และ observation ไม่ atomic กับ snapshot รอบ.

การตรวจ ownership แบบไม่มี binding เพิ่ม D1 SELECT สองครั้งต่อการตรวจ เพื่อกัน handoff ที่สถานะไม่สอดคล้องและตรวจซ้ำหลังอ่าน notice. Probe บน Miniflare แบบ stub notice ครั้งเดียววัด 5 checks = 15 SELECT รวม 189 ms; ตัวเลขนี้ไม่แทน latency/โควตา Cloudflare หรือ workload legacy หลาย DETAIL และต้องทดสอบก่อน merge. Worker mock + local D1 ผ่าน 8 กรณีรวม duplicate delivery และ provider จำลองตอบหายที่ DAILY/RAW/DETAIL แต่ยังไม่ใช่การ kill process จริง.

## ความคืบหน้าทดลองเพิ่มเติม 22 พ.ย. 2026

รอบ mock ปิดแบบผสมได้เฉพาะ PARKED (มีหลักฐาน hold และ mock handoff ไปสมาชิกถัดไป), NOT_STARTED (positive birth/generation และตรวจหลักฐานปัจจุบันครบ) และ RECONCILE; ผู้เรียกใช้ต้องเปิด flag ทดลองและ `APP_ENV=test` และ barrier ทุกตัวปิดโดยค่าเริ่มต้น ผลดังกล่าวบอกเหตุการณ์ที่บันทึกไว้ ไม่ให้สิทธิ์เขียนหรือยืนยันว่า provider ปลอดผู้เขียนจริง. D1 จำลองทดสอบ 100 สมาชิก, แข่งปิด/lease, ACK หาย, หลักฐาน/notice/revocation เปลี่ยนและ guard หาย; บางกรณีสร้าง claim ว่างและ notice ด้วย DDL ใน fixture จึงไม่ใช่ Worker/provider end-to-end หรือหลักฐาน production.

ผล VERIFIED ยังไม่พร้อมปิด: receipt ปัจจุบันเก็บ hash และ revision แต่ไม่เก็บข้อมูลต้นฉบับทั้งหมดที่ใช้คำนวณและตรวจ completion ทำให้ D1 ตรวจผล VERIFIED ที่ commit แยกก่อนปิดซ้ำไม่ได้ครบเมื่อหลักฐานเปลี่ยน. `serial_pilot_verified_close_not_ready` และ base transition จึงปิดทางปิด VERIFIED รวมทั้งกรณี barrier หาย; test legacy ที่ถอดทั้งสอง guard เป็นการสำรวจเท่านั้น. งานถัดไปคือเก็บ canonical proof inputs แบบ immutable รวม source, exact journal/operation/preimage/marker และ expected set, ตรวจเท่ากับข้อมูลปัจจุบันพร้อม claim/epoch/edge/guard ในธุรกรรมปิด แล้วทดสอบผล commit แยก→หลักฐานเปลี่ยน, แข่ง claim/close, ACK หาย และหลาย DETAIL. D1 ไม่รับรองตัวผู้สร้าง hash หรือ provider readback จึงยังอาศัย Worker/D1/DDL ที่เชื่อถือได้และ external fence ต่อเนื่องตาม gate #296. การอ่านข้ามรุ่นยังเป็น read-only; ยังไม่มีสิทธิ์ส่งต่อจากหลักฐานข้ามรุ่น. เอกสาร flow/published views, full check และ dry-run ยังต้องทำเมื่อ behavior สมบูรณ์.
