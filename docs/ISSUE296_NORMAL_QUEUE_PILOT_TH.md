# ทดลองส่งหนึ่งรายการในคิวปกติ #296

## ผลจบของการตรวจและการทดลอง

ที่ฐาน 7c5c91d ตัวรันจบ HANDOVER_ONE ทันทีที่จองงาน และ INSPECT_HANDOVER ตรวจเฉพาะขั้นส่งมอบ จึงไม่มีผลจบรอบที่เทียบทั้งงานกับแถวจริง ความเสี่ยงคือรายงานสำเร็จเร็วเกินไปหรือส่งคำสั่งเขียนซ้ำหลังผลไม่ชัดเจน ตัวแก้ตรวจหลักฐานหลัง SETTLE และติดตามงานทดลองแบบจำกัดเวลา เกณฑ์ผ่านคือทั้งงานและรอบปิดแล้ว พร้อมผลอ่านแถวที่ตรงกับ D1 งานเดิมที่เจ้าของให้ข้ามยังคงสถานะ REVIEW และ failed job เดิม

## ขอบเขตงานทดลอง

ผลสำเร็จของงานทดลองยืนยันประวัติการปิด DAILY, RAW และ DETAIL ที่เกี่ยวข้อง และเทียบค่า DAILY ปัจจุบันกับ D1 อีกครั้ง ตัวรันตรวจหลักฐานต้นทางก่อนและหลังอ่านชีต การติดตามต้องใช้ Worker รุ่นเดียวกับที่รับช่วง หากเปลี่ยนรุ่นให้ตรวจหลักฐานแยกและรักษาสิทธิ์ที่จองไว้

เมื่อผล SETTLE ไม่ชัดเจน ตัวรันอ่าน INSPECT อีกครั้งและเทียบ fingerprint กับ preimage ของรายการเดิม หากยืนยันไม่ได้จะจบรอบด้วยข้อผิดพลาดและเก็บงานเดิมไว้ใน REVIEW เมื่อ HANDOVER_ONE จองงานสำเร็จ ตัวรันเฝ้าดูสถานะงานที่จองผ่าน FINISH_STATUS หากคำตอบของการจองหาย จะตรวจ audit ของงานเดิมที่เลือกก่อนติดตามต่อ

ตัวรันตรวจทันทีและรอได้อีก 15 รอบ รอบละหนึ่งนาที เมื่อทั้งงานและ epoch ปิดแล้ว ให้อ่านแถวรายวันจริงและตรวจสถานะซ้ำก่อนรายงานความสำเร็จ ถ้างานอยู่ใน REVIEW หรือ FAILED ให้ลองอ่านแถวรายวันครั้งเดียวและรายงานทั้งสองผล รอบที่หมดเวลาหรือหลักฐานไม่ชัดเจนจบด้วยเหตุผลใน GitHub Actions และเกิด exit code ที่ไม่สำเร็จ การจบรอบติดตามไม่แก้สถานะงาน ผู้ดูแลใช้ FINISH_PILOT ตรวจต่อโดยอ่านอย่างเดียวได้ การขยายไปงานอื่นยังต้องผ่านขั้นตอนเดิม

เกณฑ์รับงานคือเลือกเฉพาะงาน PENDING ที่ระบุจากเดือนปัจจุบัน อ่านแถวจริงเทียบ D1 ก่อนขยาย เก็บรายการเดิมใน REVIEW และรักษาข้อมูลธุรกรรม ความเสี่ยงสูงเนื่องจากการเปิด epoch ใน D1 อนุญาตให้คิวปกติเริ่มเขียนรายงานได้

ที่ฐาน 0c08c6c คิวปกติและ cron หยุดเมื่อพบ workbook claim ใน REVIEW ส่วนตัวเลือกอัตโนมัติเดิมเปิดงานถัดไปได้หลังจบ epoch แรก การทดลองจึงต้องปิดการเลือกอัตโนมัติ คง recovery gate และ pacing ตรวจ Worker รุ่นเดียว 100% และรอผู้เขียนเดิมหยุด ก่อนส่งคำสั่งต้องตรวจการพัก incident, หลักฐาน DAILY และ notice ตามกระบวนการกู้

เส้นทาง `POST /admin/stable-sync/normal-expense-pilot` รับ `HANDOVER_ONE` หรือ `INSPECT_HANDOVER` พร้อม admin authentication และ header `x-malipang-expected-worker-version` ต้องเปิด `CONTINUOUS_NORMAL_QUEUE_PILOT_ENABLED=true` ปิด `CONTINUOUS_NORMAL_EXPENSE_RECOVERY_ENABLED=false` และเปิด recovery gate งานที่เลือกต้องเป็น CONFIRMED รุ่น 1 หลัง cutover ในเดือนปัจจุบันตามเวลากรุงเทพฯ

หลังจองแล้วต้องคง recovery gate และตรวจผลผ่าน D1 และชีตก่อนขยายงาน การปิดฟังก์ชันทดลองไม่ยกเลิก epoch ที่เปิดอยู่

## การรับช่วงป้ายพักแก้ไขจากรายการที่ตรวจแล้ว

เมื่อ DAILY ของรายการเดิมได้รับการยืนยันและมี preimage แล้ว ผู้ดำเนินการใช้ `HANDOVER_ONE` กับงานทดลองหนึ่งรายการ พร้อมระบุ fingerprint, preimage digest และ Worker version ที่ตรวจแล้ว ต้องคงรั้วผู้เขียนภายนอกและผู้เฝ้าดูตลอดการตรวจจนได้ผลอ่านกลับ ขั้นนี้มีความเสี่ยงสูง และต้องปฏิบัติตาม release gates ของ Production

Worker ตรวจข้อมูล D1 แถวในชีตและป้ายพักอีกครั้ง จากนั้นบันทึกการส่งมอบใน `admin_audit` เปลี่ยนจาก claim เดิมเป็น claim ของงานทดลอง และเปิด epoch ด้วย D1 transaction เดียว หากรับงานไม่ได้ให้ย้อนทั้ง transaction รายการเดิมยังเป็น REVIEW และ failed job ยังเป็น OPEN

ตัวส่งปกติรับป้ายเดิมหลังได้ lease ของงานทดลอง ผ่าน pacing และตรวจ B1/C1 ทั้งข้อความ เวลา ตำแหน่ง และรูปแบบ งานตรวจทั้ง projection, marker, หลักฐานการเขียนและ preimage ก่อนส่งป้ายพร้อม สำหรับการซ้อม ให้ตรวจกรณี lease ผิด ป้ายเปลี่ยน และรับงานไม่ได้หลังลบ claim ภายใน transaction

หากคำตอบ HANDOVER_ONE ไม่ชัดเจน ใช้ `INSPECT_HANDOVER` กับ fingerprint และ jobId เดิม ตรวจ `RESERVED`, `ADOPTED` และ `STAGE_VERIFIED` ตามลำดับ เมื่อเจอ `HELD` ให้ตรวจ claim, epoch, job, ป้าย และเหตุโดยคง gate ไว้ การยืนยัน DAILY เป็นหลักฐานเฉพาะแถวรายวัน ต้องตรวจ RAW, DETAIL และสถานะ COMPLETED ของงานแยก การย้อนโค้ดหลังจองต้องคง gate และป้ายพักจนกว่าจะตรวจหลักฐานและจัดการ claim ที่ถืออยู่

ขั้น READBACK ตรวจสูตร ยอด วันที่ รายละเอียด หมวดหมู่ และกระเป๋าเงินจริงเทียบกับ D1 และอ่านแถวที่เลือกกับคอลัมน์ marker ซ้ำก่อนสรุป หากข้อมูลต้นทางหรือแถวเปลี่ยนระหว่างตรวจ ให้ถือว่า UNVERIFIED ผลตอบผู้ดูแลแสดงเฉพาะสถานะและ Worker version

## UAT และการทดลองบน Production

1. ในระบบทดสอบที่แยกข้อมูล ให้ใช้รายการตัวอย่างที่มี DAILY intent และสถานะ REVIEW ตรงกับกรณีจริง พร้อมงาน PENDING ที่รออย่างน้อยสองรายการ ใช้รูปแบบแท็บเดิมและบัญชีบริการที่ได้รับสิทธิ์ เขียนผลเทียบก่อนและหลัง ทั้งค่าที่แสดงบนชีตและสถานะใน D1
2. เมื่อเปิด recovery gate ให้ปิดการเลือกงานอัตโนมัติและตัวส่งรายเดือน เปิด operator พิสูจน์ DAILY และโหมดทดลองเพียงงานเดียว รอให้ Worker รุ่นก่อนหยุดทำงานและตรวจการงดผู้เขียนอื่นก่อนส่งมอบสิทธิ์ตรวจไฟล์
3. ใช้ workflow normal queue pilot ซึ่งตรวจ main SHA และรุ่น Worker ที่รับ traffic ทั้งหมด เรียก PROBE เพื่อตรวจรายการเดิม ถ้าตรง ให้ SETTLE เพื่อบันทึกเฉพาะหลักฐาน การส่งงานเดิมที่อยู่ใน REVIEW ซ้ำทำให้หลักฐานคลาดเคลื่อนได้
4. HANDOVER_ONE ต้องพบรายการที่เข้าเกณฑ์เพียงรายการที่เลือกและใช้ผลสำรองกับ restore ที่ผ่านสำหรับ SHA นั้น การสำรองที่ได้รับอนุญาตหนึ่งครั้งใช้หลักฐานเดิมของรอบนั้นได้ทั้งสองขั้น คำตอบ RESERVED หมายถึงคิวรับสิทธิ์เริ่มงานแล้ว
5. ตรวจ INSPECT_HANDOVER และ READBACK ด้วยบัญชีของ Worker พร้อมตรวจ job, epoch, operation, failed jobs และจำนวนรายการรอที่เหลือ แถวที่ผ่าน READBACK ยืนยัน DAILY เท่านั้น งานที่ยังมี RAW หรือ DETAIL ค้างให้รายงานแยก เมื่อผลเขียนไม่แน่ชัดให้คงรายการไว้เพื่อตรวจต่อ
6. หยุดการขยายเมื่อ source หรือแถวที่อ่านกลับเปลี่ยน งานอื่นได้รับสิทธิ์โดยไม่คาดหมาย หรือ worker version เปลี่ยน หลังเกิดความไม่แน่ชัดให้ใช้เพียงการอ่านหลักฐาน เก็บ REVIEW, audit และ preimage เพื่อกู้ต่อ การย้อน Worker รุ่นเดิมที่ปิด gate ขณะมีงานจองอาจปล่อยคิวทั้งไฟล์ ต้องยืนยันว่ารุ่นที่กู้ต่อคง gate และรองรับสิทธิ์ที่ยังค้างก่อนเปลี่ยน traffic

รอบ Production จะเริ่มหลัง UAT และการทบทวน release ของรุ่นนี้ผ่าน ด้วยขั้น ขนาดการส่ง และหลักฐานเช่นเดียวกัน ก่อนขยายงาน 29 รายการที่สร้างก่อน cutover ให้ตรวจประวัติแถวเก่าและจัดทำวิธีนำเข้าแท็บใหม่โดยเก็บประวัติการซิงก์เดิมไว้


## RUN_SERIAL

[ลำดับการเรียก LINE, Worker, D1 และ Google Sheets พร้อมวิธีรับช่วงเมื่อคำตอบหาย](system-flow/serial-sequence.md)

ผู้ดูแลเลือก `RUN_SERIAL` ใน workflow เดิมสำหรับการส่งต่อเนื่อง เมื่อเงื่อนไข release, UAT, สำรอง/กู้คืน SHA นั้น การกันผู้เขียนอื่น และการเฝ้าดูของเจ้าของครบตามขั้นเดิม [แผนผังการส่งต่อ](system-flow/serial-expense.svg)

1. ตัวรันอ่านชุดงานรอของเดือนปัจจุบันตามเวลาไทยจาก D1 เลือกเฉพาะค่าใช้จ่ายที่ยืนยันแล้ว รุ่น 1 หลัง cutover ซึ่งถึงเวลาทำและยังไม่มีการลองส่ง งานก่อน cutover ยังใช้กระบวนการกระทบยอดเดิม
2. ถ้ายังไม่เคยจอง ให้ตรวจ DAILY ของ A และยืนยันหลักฐานตามขั้น PROBE/SETTLE ก่อน HANDOVER_ONE งาน A คง REVIEW และเก็บ failed job เดิมไว้ หากเคยจองแล้ว ตัวรันอ่านสายการส่งมอบและเริ่มจากงานล่าสุด
3. สำหรับ B ต้องเห็น job และ epoch ปิดครบ อ่าน DAILY ของ B ผ่านบัญชี Worker เทียบ D1 และอ่านหลักฐานซ้ำ เมื่อยังมี C ในชุด ตัวรันส่ง ADVANCE_ONE ระบุ B, หลักฐานงานจบ และ C ตัว Worker อ่านชีตเองอีกครั้งและตรวจ D1 ในธุรกรรมจอง มีการจองต่อจาก B ได้ครั้งเดียว
4. เมื่อคำตอบการจองหาย ให้อ้างประวัติการส่งมอบ B → C ที่ตรงทุกค่า ถ้างานพัก ล้มเหลว แถวไม่ตรง หลักฐานเปลี่ยน หรือหมดเวลารอ ให้จบรอบพร้อมจำนวนในชุดที่ยืนยันและค้าง การเริ่ม RUN_SERIAL รอบใหม่ต้องตรวจงานที่จองล่าสุดก่อน จำนวนที่ตรวจในรอบอาจรวมงานที่ตรวจซ้ำ จึงห้ามนำจำนวนจากหลาย run มาบวกเป็นจำนวนแถวใหม่
5. สำหรับ UAT ใช้ A ที่ยังพัก กับ B และ C ที่เข้าเกณฑ์ ตรวจ A คง REVIEW ตรวจ B และ C ทีละแถวหลังประมวลผล รวมถึงจำลองคำตอบหายและแถว B ไม่ตรง ถ้า B ยังไม่ผ่าน C ต้องไม่ได้สิทธิ์ เก็บผลแยกจาก Production

ถ้าต้องหยุดการส่งต่อ ให้หยุดตัวรันแล้วใช้ FINISH_PILOT ตรวจงานล่าสุดในสายแบบอ่านอย่างเดียว แม้ยังมีงานอื่นรอก็จะไม่จองเพิ่ม คง gate และ Worker รุ่นเดิมไว้ เพราะประวัติการจองผูกกับ Worker version ที่สร้างประวัตินั้น หากเปลี่ยนรุ่นกลางสายต้องตรวจหลักฐานเพื่อกู้เฉพาะงานก่อนขยาย ห้ามใช้ผล READBACK แบบไม่ระบุรายการตัดสินงานถัดไป

ตัวส่ง DAILY ตรวจแถวว่างที่เกิดจากการเพิ่มและเลื่อนช่วงท้ายแท็บทั้งในมุมสูตรและค่าที่แสดง ยอมรับแถวว่างติดกันที่ปลายช่วงที่เลื่อน ตรวจคอลัมน์งบประมาณตามตำแหน่งเดิม และคงการพักงานเมื่อพบช่องว่างแทรกกลางส่วนสูตรหรือผลอ่านกลับไม่ตรง

## ร่าง #348: ตรวจรอบและผลจำลองในเครื่อง

อ่าน [acceptance audit](ISSUE348_ACCEPTANCE_AUDIT_TH.md) และ [sequence ล่าสุด](system-flow/serial-sequence.md#6-รอบจำลอง-348-พัก-b-จอง-c-และบันทึกผล) ก่อนใช้หลักฐานจาก branch นี้. ขอบเขตที่อนุญาตคือพัฒนา ทดสอบในเครื่อง และ dry-run; การเขียน Google/D1 จริงและการปล่อยรุ่นต้องผ่าน authority และ gate ของ #296 แยก. ตัวอย่าง mock oracle และ fence ไม่พิสูจน์การหยุด writer, มนุษย์ หรือ provider request จริง และ migration barriers คงปิด.

`HOLD_RESERVED` เก็บ B ใน REVIEW พร้อม claim/epoch; RUN_SERIAL ใน local test รับ coordinator ที่ฉีดเพื่อเรียก helper จำลอง attestation และ CAS ส่งสิทธิ์ C เมื่อหลักฐานตรง; CLI ปกติไม่มี coordinator และไม่ใช่คำสั่งที่ได้รับอำนาจใช้งานจริง. C อาจต้องผ่าน DAILY, RAW, DETAIL หลายรายการ และ FINAL; หากผล provider หรือ notice ไม่ชัดให้เก็บ claim และ intent แล้ว reconcile โดยไม่ส่งซ้ำ. สถานะ READY ใน Sheets อาจเกิดก่อนคำตอบ D1 จึงต้องมี external fence ที่พิสูจน์แล้วต่อเนื่องจนกว่าจะ reconcile.

ก่อนเซ็น attestation และก่อนส่ง batch โอนสิทธิ์ ให้ตรวจซ้ำว่า B ยังไม่เคยลองทำและไม่มีหลักฐานผลข้างเคียง ถ้าพบหลักฐานที่ขัดกันก่อนเซ็น context เป็น null ให้หยุดโดยงดเซ็นและงดเรียกจอง C ถ้าพบหลังเซ็นแต่ก่อนส่ง batch ให้ helper คืน HELD โดยงดส่ง batch หากพบใน batch ธุรกรรมจะ rollback และเก็บ claim เดิม เมื่อได้ UNCERTAIN ให้หยุดจอง ตรวจ audit/round/claim ของรอบเดิม และห้ามส่งซ้ำ

รอบแบบทดลองของ `RUN_SERIAL` เปิดได้เฉพาะ local test ที่ฉีด durable identity store และใช้ localhost: store สร้าง marker แบบไม่ทับก่อน SETTLE/OPEN ผูก roundId กับ scope ของ workbook/Worker; หาก marker เดิมมีอยู่หรืออ่านไม่ชัด ให้หยุดและตรวจ roundId เดิม ห้ามสร้างรอบใหม่จาก `LIST_OPEN` ว่าง. CLI/workflow ปกติไม่ได้ฉีด store จึง fail closed ใน round-mode. Store ทดลองเป็นไฟล์เฉพาะเครื่อง ต้องรักษา directory เดิม; ไม่พิสูจน์การประสานข้ามเครื่องหรือการหยุด writer.

ใช้ `RECOVER_ROUND` กับรหัสรอบเดิมหลังตัวรันหยุดหรือคำตอบหาย แม้ยังพิสูจน์ไม่ได้ว่ากันผู้เขียนรายอื่นได้แล้ว ตัวรันตรวจสิทธิ์, SHA และรุ่น Worker ที่รับ traffic 100% แล้วส่ง `READ` ครั้งเดียว. Workflow ยังผ่าน GitHub Environment `production`. การสำรองเพื่อเขียนและการรับรองผู้เขียนภายนอกใช้กับขั้นที่แก้สถานะ.

- **OPEN** หาก audit, snapshot การจอง, epoch, admission และหลักฐานการส่งต่อของสมาชิกตรงกัน สรุปจะแสดงสายการจองที่บันทึกไว้ เช่น B → C พร้อมรุ่น Worker ผู้จอง ให้ติดตามงานปลายสายและตรวจ claim กับ journal ของงานเดิม ขั้น VERIFIED ที่แสดงเป็นหนึ่งในขั้นที่อาจมีเวลาเดียวกัน หากหลักฐานขาดหรือขัดกัน ให้คงสถานะไม่แน่ชัดและพักรอบไว้ คำขอเดิมอาจยังทำงานอยู่แม้เห็นเพียง B หรือยังไม่พบการจอง
- **CLOSED** หากคำตอบปิดรอบหาย ให้อ่านผลที่บันทึกไว้ในรอบเดิมได้ทั้งผล VERIFIED พร้อม receipt, ผลจำลองที่จำแนกแล้ว, ผลที่ต้องกระทบยอด และรอบว่าง การอ่านข้ามรุ่นหรือเดือนให้เพียงประวัติเดิม ต้องตรวจหลักฐานปัจจุบันแยกก่อนพิจารณาสิทธิ์เขียน

เมื่อเริ่ม `RUN_SERIAL` ใหม่แล้วพบรอบ `OPEN` กับ tip ที่จองไว้ ตัวรันอ่านผลและ receipt เดิม แต่หยุด RECONCILE ก่อน `RECORD_VERIFIED`, `ADVANCE_ONE` หรือ `CLOSE` แม้ receipt ตรง เพราะคำขอจาก process เดิมอาจยังไม่สิ้นสุด หากรอบเดิมปิดแล้วใช้ `READ_ROUND` กับ roundId เดิมเพื่ออ่านผลย้อนหลัง; การอ่านไม่ใช่สิทธิ์เขียน และห้ามอนุมานจากไม่พบข้อมูลครั้งเดียวว่าคำขอเก่าจบแล้ว.

ผลรอบจำลองแยก VERIFIED (หลักฐาน v2 ณ เวลาตรวจ), PARKED (B พักและ mock handoff ไป C ถูกบันทึก), NOT_STARTED (positive provenance ว่าไม่เริ่มภายใต้ guard ที่ตรวจ) และ RECONCILE (หลักฐานยังไม่พอ). ผลจบรอบไม่ได้หมายความว่าทุกรายการสำเร็จ. `CLOSE_MOCK_ROUND` เป็น phase เฉพาะ localhost ที่ต้องตั้ง `PILOT_LOCAL_MOCK=true` และ Worker `APP_ENV=test`: อ่านรอบก่อน หาก OPEN ต้องมี coordinator จำลองที่ฉีดมายืนยัน quiescence ผูก round/รุ่น/fence/nonce ก่อนส่งหนึ่งครั้ง หากไม่มีหรือไม่ชัดให้หยุด; หาก CLOSED อ่านผลเดิม หลังคำตอบหายตัวรันอ่านรอบเดิม ไม่ส่งคำสั่งปิดซ้ำ. CLI ปกติไม่มี coordinator นี้. Phase นี้ไม่ได้เปิดใน workflow ปฏิบัติการ. สำหรับการทดลอง transport แบบ synthetic เท่านั้น `node tests/helpers/serial-local-mock-cli.mjs` ใช้ฐาน SQLite ชั่วคราวและ coordinator ใน fixture; ไม่รับ URL/key และไม่รัน Worker หรือ D1 จริง.

`READ_ROUND` และ `READ_HISTORICAL` ใช้อ่านข้อมูลเดิมข้ามรุ่น/เดือนเท่านั้น ไม่ยืนยันค่า Sheets ปัจจุบันและไม่ให้สิทธิ์จองต่อ. หาก snapshot, proof รุ่น v2, epoch หรือ audit ขาด/ขัดกัน ให้หยุดและตรวจ D1/claim/journal; ห้ามตีความการไม่มีแถวหรือ claim ในการอ่านครั้งเดียวว่า provider หยุดเขียน. การกู้จนปิดครบหลัง process kill และสายสิทธิ์ข้ามรุ่นยังต้องพิสูจน์ตาม acceptance audit.
