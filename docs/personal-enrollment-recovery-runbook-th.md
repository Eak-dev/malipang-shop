# แนวทางกู้การผูก ID รายการส่วนตัวที่ผลไม่แน่ชัด — ฉบับรอทดสอบ

ขั้นตอนนี้อยู่ใน source แบบปิดเป็นค่าเริ่มต้น ยังไม่อนุญาตเปิด production จนตรวจ native Google rowMetadata, ทดสอบ D1/Google ร่วมกัน, ตรวจการระบาย writer เก่า, retention และ rollback แล้ว. ใช้เฉพาะการผูก metadata ของ personal RAW ที่มี lock/identity/outer อยู่ใน REVIEW; ไม่ใช่วิธีกู้รายการค่าใช้จ่ายทั่วไปหรือชีตรายวัน และไม่รองรับรายการก่อน cutover watermark ในขณะนี้

ผู้ดูแลใช้ credential `/admin/*` ที่มีอยู่ โดย endpoint ทั้งหมดเป็น POST ภายใต้ `PERSONAL_RECOVERY_ADMIN_ENABLED=true`; ขั้น resolve ยังต้องเปิด `PERSONAL_RECOVERY_RESOLVE_ENABLED=true` โดยการเปิดค่าเหล่านี้ยังไม่ผ่านการอนุมัติ deployment. Credential ปัจจุบันเป็น token ใช้ร่วมกัน บันทึกได้เพียง `ADMIN_TOKEN` ไม่สามารถพิสูจน์ตัวบุคคลแต่ละคนจาก credential นี้ ต้องจัดการสิทธิ์และการหมุน token ตามระบบเดิม; ห้ามใส่ token หรือข้อมูลส่วนตัวลง reason หรือ log

1. ประสานให้พักแก้ไขแท็บ personal ชั่วคราวและยืนยันว่า writer เก่าถูกหยุด/ระบายจริง ตรวจสถานะงาน personal ที่ยัง PROCESSING/IN_FLIGHT ให้หมด; ระบบยังไม่มี hard lock ที่ป้องกันเจ้าของ Google Sheet แก้ไขได้ นี่คือการประสานกัน ไม่ใช่ Google CAS
2. เรียก `/admin/personal-enrollment-recovery/inspect` ด้วย `{ "personalUseId": "personal_..." }`. ผลแสดงข้อมูลต้นทางที่จำเป็น สถานะ lock/identity/outer และผลอ่าน provider; ไม่มีเลขแถวหรือ secret. `READBACK_MATCHED` หมายถึง ID เดียว marker เดียวและค่าที่ตรวจตรง source ขณะอ่านเท่านั้น หากไม่ตรง/อ่านไม่สำเร็จ ให้ตรวจและแก้สาเหตุก่อน แล้ว inspect ใหม่ ห้ามส่งคำขอ Google เดิมซ้ำ หรือเดาว่าไม่มีการเขียนเมื่อหมดเวลา
3. เมื่อ MATCHED และทั้งสามสถานะเป็น REVIEW ให้เรียก `/admin/personal-enrollment-recovery/approve` ด้วย `{ "personalUseId": "personal_...", "evidenceDigest": "<ค่าจาก inspect>", "reason": "เหตุผลสั้น ๆ" }`. ระบบอ่าน source/provider ใหม่ และบันทึก approval กับ `admin_audit` ใน transaction เดียว คำอนุมัติหมดอายุใน 10 นาที; หากหมดอายุให้ inspect และ approve ใหม่ ไม่ใช้หลักฐานเก่า. หากคำตอบ approve หาย ให้ inspect ซ้ำและดู `pendingAction` เพื่อค้น action ที่บันทึกแล้ว โดยไม่ส่ง Google ซ้ำ
4. หลังพักแก้ไขและระบาย writer เก่าแล้ว เรียก `/admin/personal-enrollment-recovery/resolve` ด้วย `{ "actionId": "<ค่าจาก approve>", "editorsPaused": true, "legacyWritersDrained": true }`. คำยืนยันเป็นความรับผิดชอบของ admin และบันทึกใน audit; ไม่บังคับให้ผู้แก้ทุกคนกด ACK ระบบอ่าน source/provider ซ้ำ ตรวจ ID/marker/ค่าและ D1 revision, ตรวจว่าไม่มี personal worker กำลังทำงานและไม่มี REVIEW เก่าของรายการ แล้วเปลี่ยนสถานะ identity/outer/jobs พร้อมปลด lock และบันทึก audit แบบ transaction เดียว คำสั่งนี้ไม่มี Google Sheets POST และไม่ replay
5. หาก resolve ตอบ `OUTCOME_UNKNOWN` ให้เรียก `/admin/personal-enrollment-recovery/status` ด้วย `{ "actionId": "..." }`; `APPLIED` เป็นหลักฐานว่าการเปลี่ยน D1 ครั้งนั้น commit แล้ว ไม่ใช่การรับรองว่า Google Sheet จะไม่ถูกแก้ในภายหลัง; `APPROVED` หมายความว่ายังไม่พบผล commit และ `EXPIRED` หมายความว่าคำอนุมัติหมดอายุ ห้ามเดาว่าปลอดภัยหรือรีบส่งซ้ำ ให้ตรวจ source/provider และสถานะ worker ใหม่ก่อนตัดสินใจ

หากต้องการถอนคำอนุมัติที่ยังไม่ถูกใช้ ให้เรียก `/admin/personal-enrollment-recovery/cancel` ด้วย `{ "actionId": "...", "reason": "เหตุผลสั้น ๆ" }`; ระบบบันทึก audit โดยคง lock และไม่เขียน Sheets. หากคำตอบหาย ให้ดู `status` ก่อนดำเนินการต่อ; คำอนุมัติที่ยกเลิกแล้วใช้ resolve ไม่ได้

การทดสอบ SQLite ภายในเครื่องไม่พิสูจน์พฤติกรรม D1 จริง, metadata ที่มองเห็นเฉพาะ Google project อื่น, คนย้าย/partial sort ระหว่างอ่านกับเขียน หรือการกู้กรณี marker หาย/ID ซ้ำ/ค่าต่าง. กรณีเหล่านี้ยังต้องตรวจเป็นรายกรณี และอย่าลบ marker หรือปลด lock ด้วยการแก้ฐานข้อมูลตรง ๆ. ตาราง audit/action และ registry ต้องมีนโยบายอายุเก็บ การ archive และ rollback ที่รักษาหลักฐานก่อนนำขึ้นจริง
